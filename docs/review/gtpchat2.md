Принял текущую модель исполнения за базу. # 7. ORC: ретест-лимит против входа по close

### Да, структурная причина adverse selection есть — и она прямо следует из кода

ORC сначала ждёт **закрытия бара пробоя**, потом ставит pending-limit на уровень диапазона; исполнение происходит только если будущий бар вернулся к этому уровню.  

Критическая часть:

```go
p := s.pending
fill, filled := p.fillPrice(candle)
if !filled {
	return nil
}
```



и сам fill:

```go
if candle.Low > p.limitPrice {
	return 0, false
}
return math.Min(candle.Open, p.limitPrice), true
```



То есть сравниваются **не одни и те же события**:

`close-entry` получает весь набор breakout-сигналов;

`retest-limit` получает только подмножество, где после breakout рынок вернулся к уровню.

**Предполагаю:** это и есть структурный adverse selection. Сильный breakout, который сразу продолжился, часто не возвращается к уровню — он уходит без сделки. А сделка появляется именно тогда, когда рынок уже показал желание вернуться к breakout level. В худшем случае такой возврат является ранним признаком failed breakout.

При этом у ретеста есть и плюс: цена входа лучше. Поэтому вопрос не «лимит всегда хуже», а **перекрывает ли улучшение цены отрицательный conditional selection**.

### Как проверить на имеющихся данных

Не нужно заново оптимизировать ORC. На всех breakout-сигналах построить три класса:

1. **No-touch:** после breakout close уровень диапазона в течение часа не был затронут.
2. **Touch + continuation:** уровень затронут, но после fill движение продолжается.
3. **Touch + failure:** уровень затронут, затем движение ломается.

Для каждого breakout-сигнала построить две counterfactual сделки:

* **Close:** вход по `breakout close`;
* **Retest:** текущий лимит.

Стоп, TP, trailing и EOD — одинаковые. Сравнивать `net exp_R`, MFE/MAE и долю сделок. В частности, важна величина

`E[R | retest fill] − E[R | all breakout signals]`.

Если условие ретеста действительно adverse-selects, она будет отрицательной.

Дополнительно сделать этот разрез по `MGNT/ROSN/TATN` отдельно от остальных бумаг, потому что текущие ORC-ограничения и whitelist уже предполагают разную пригодность тикеров. 

### Практический вывод

Я бы **не переподбирал сейчас пороги ретест-лимита как единственную ORC-гипотезу**. Сначала провести A/B:

`breakout-close` vs `breakout → retest-limit`.

Если close-entry даёт устойчиво больше `net exp_R` на одном и том же сигнал-сете, вопрос о дальнейшем тюнинге лимита почти отпадает.

# 8. Насколько верить `or-fade` и `mf-afternoon`

## `or-fade`: сейчас не верить

Сам код реализует именно гипотезу «сначала сильный breakout, потом его failure»:

```go
case close > s.orbHigh*(1+th):
	s.watch = &orFadeWatch{
		direction:      "up",
		startedAt:      candle.Timestamp,
```



А затем для `RequireInsideRange=false` вход SELL возникает уже при возврате close ниже OR high:

```go
if s.opts.RequireInsideRange {
	failed = close <= s.orbHigh && close >= s.orbLow
} else {
	failed = close < s.orbHigh
}
```



Это разумная рыночная гипотеза: failed breakout может mean-revert. Но текущая настройка имеет дополнительную проблему: `reward_ratio=1.27095`, а `trail_activation_r=2.00393`. 

Трейл активируется только при достижении `ActivationR`:

```go
triggerR := cfg.ActivationR + float64(stage-1)*cfg.DiscreteStepR
if !triggerReached(pos, price, triggerR) {
	continue
}
```



А TP срабатывает уже на уровне `rewardRatio·R`. 

Значит текущий trailing у `or-fade` фактически мёртв.

Ещё важнее: старый чемпион уже показал деградацию `+0.240` на подборе → `+0.096` на OOS; сам протокол отдельно помечает это как проблему, которую переподбором не удалось объяснить. 

### План проверки `or-fade`

Ничего не оптимизировать.

**Первый слой:** текущая конфигурация, честная модель, 1 б.п. slippage, период `2026-04-01 → 2026-09-11`.

**Второй слой:** тот же запуск при 2 б.п.

**Разрез:** три последовательных окна примерно по 6–8 недель, без выбора лучшего.

**Минимум:** `60` сделок на полном validation-срезе; это реалистично относительно старых `62` сделок на отложенном хвосте. В протоколе уже используется минимум 20, но для принятия именно этого слота я считаю 20 слишком слабой планкой. 

### Что означает «не верить»

Я бы **не считал `or-fade` подтверждённым**, если выполнено хотя бы одно:

* `net exp_R <= 0` на полном validation при 1 б.п.;
* два из трёх временных окон дают `exp_R <= 0`;
* при 2 б.п. преимущество исчезает полностью;
* или OOS снова получается заметно хуже in-sample.

Последний пункт уже один раз произошёл, поэтому повторение было бы сильным отрицательным сигналом.

---

## `mf-afternoon`: пока держать, но не оптимизировать

MF — не просто ORC-клон. Он строит breakout по предыдущей истории:

```go
upper, lower, ok := rangeLevels(s.buffer.history)
...
case close > upper*(1+th):
	direction = "BUY"
```



Затем есть trend-фильтр SMA:

```go
if s.opts.TrendSMAPeriod > 0 {
	sma := calcSMA(s.buffer.history, s.opts.TrendSMAPeriod)
...
	if direction == "BUY" && close <= sma {
		return nil
	}
}
```



И текущая конфигурация — `lookback=39`, breakout threshold около `76.6 б.п.`, `long_only=true`, SMA 37, volume filter выключен. 

Это уже отдельная гипотеза: **не просто breakout, а достаточно большой delayed momentum move в long-only режиме**.

Но 46 сделок — слишком мало для нового перебора. Плюс текущий трейл опять фактически недостижим: `2.517R` против TP `1.394R`. 

### План проверки `mf-afternoon`

Здесь я бы сделал наоборот: **параметры заморозить**.

Период проверки: минимум **12 месяцев подряд**, лучше `2025-10 → 2026-09`, чтобы получить достаточно наблюдений.

Минимум: **20–25 сделок**. Если меньше — результат назвать **inconclusive**, а не «успехом».

Разбить период на четыре последовательных квартала и смотреть `net exp_R` каждого.

### Что означает «не верить»

* полный 12-месячный OOS `exp_R <= 0`;
* или три из четырёх кварталов `<= 0`;
* или после 2 б.п. slippage результат становится отрицательным.

При `n<20` я бы не делал вывод ни «держать», ни «выключать» по одной только прибыльности: это просто недостаток данных.

# 9. Что ещё тестировать на 10 ликвидных TQBR

При текущей модели расходы примерно:

* комиссия: `0.008% × 2 = 1.6 б.п.`;
* slippage: `1 б.п. × 2 = 2.0 б.п.`;
* итого **3.6 б.п. round-trip**. 

Значит минимальный валовой price move, чтобы просто покрыть round-trip cost, — **3.6 б.п.**

В единицах `R` это:

|    стоп | 3.6 б.п. расходов |
| ------: | ----------------: |
| 20 б.п. |             0.18R |
| 30 б.п. |             0.12R |
| 40 б.п. |             0.09R |

Это порог без запаса. Для реального edge я бы не рассматривал гипотезу, если её наблюдаемое преимущество меньше примерно этого уровня до costs. **Предполагаю:** для TQBR с худшей ликвидностью разумный operational hurdle будет выше, но в приложенном коде этого параметра нет.

### 1. Breakout утреннего диапазона с входом по close

**Механизм:** после формирования локального диапазона новые цены отражают новую информацию/сдвиг order-flow; continuation может длиться несколько M5.

**Минимум:** `>3.6 б.п.` среднего валового движения после входа; при 30-б.п. стопе это уже `>0.12R`.

**Дешёвая фальсификация:** без оптимизации построить returns через `+1,+2,+3,+6` M5 после первого close за `ORB + X` и сравнить с контролем из всех остальных M5. Проверить 15/30/60-минутные ORB как заранее заданные точки, не искать лучший.

---

### 2. Failed-breakout reversal

Это близко к `or-fade`, но гипотезу можно сделать более простой и не привязывать к конкретной архитектуре watch.

**Механизм:** пробой уровня + возврат внутрь диапазона означает, что breakout не получил продолжения; краткосрочный order-flow может развернуться.

**Минимум:** те же `3.6 б.п.` gross; лучше искать ожидаемое движение хотя бы `6–8 б.п.` после costs, иначе edge слишком тонкий.

**Дешёвая фальсификация:** взять все breakout closes и измерить forward return после первого M5 close обратно внутрь диапазона. Никакого ATR/RR tuning на первом этапе.

---

### 3. Delayed momentum после сильного M5 impulse

Это наиболее близко к текущей `mf-afternoon`.

**Механизм:** большой односторонний M5 move может отражать не шум, а продолжение исполнения крупного потока; следующий 1–3 бара могут сохранять автокорреляцию.

**Минимум:** `>3.6 б.п.` gross forward move; при 30-б.п. стопе нужен хотя бы `0.12R`.

**Дешёвая фальсификация:** сгруппировать M5 returns по deciles абсолютной величины текущего бара и посмотреть средний `t+1...t+3` return по знаку. Это делает очень мало степеней свободы и быстро показывает, есть ли вообще continuation.

---

### 4. Волатильностное сжатие → expansion breakout

**Механизм:** после периода низкой реализованной волатильности выход из узкого диапазона может создавать кластер движения; именно размер дальнейшего движения, а не направление, даёт opportunity.

**Минимум:** для 20/30/40-б.п. стопа те же `0.18/0.12/0.09R`.

**Дешёвая фальсификация:** использовать percentile текущего ATR/range за заранее фиксированное окно, например нижние 20%, и проверить только последующий 3–6-bar range expansion. Никакой оптимизации порога внутри этих данных.

---

### 5. Time-of-day continuation/reversal

У текущего бота уже есть сильная подсказка: отдельные session ORC слоты (`07:00–09:50` и `19:05–23:50`).  

**Механизм:** ликвидность, поток заявок и поведение цены могут систематически различаться по времени дня.

**Минимум:** более 3.6 б.п. gross; для практической значимости я бы требовал минимум `6 б.п.` среднего валового движения.

**Дешёвая фальсификация:** вообще без стратегии проверить conditional forward return по 5-минутным слотам времени. Если ни в одном заранее выбранном окне нет устойчивого преимущества больше cost hurdle, строить сложную session strategy смысла мало.

# 10. Что изменить в методологии до следующего подбора

Текущий протокол делает `2024-07-03 → 2026-03-31` подбором и `2026-04-01 → 2026-09-11` OOS; trial оценивается медианой Calmar по 19 двухмесячным окнам. 

Я бы изменил четыре вещи.

## 1. Сделать настоящий nested / walk-forward протокол

Вместо одного большого train и одного хвоста:

**Первый слой, research:**
`2024-07-03 → 2025-06-30` — initial train.

Дальше четыре последовательных OOS-фолда по 3 месяца:

* `2025-07 → 2025-09`
* `2025-10 → 2025-12`
* `2026-01 → 2026-03`
* `2026-04 → 2026-06`

На каждом шаге train расширяется.

**Последний `2026-07-01 → 2026-09-11` — полностью замороженный final holdout.**

Этот последний кусок не используется ни для выбора гипотезы, ни для подбора параметров.

Это важнее, чем ещё 300 trial'ов.

---

## 2. Убрать Calmar как первичную метрику trial

Медиана Calmar по 2-месячным окнам плохо соответствует задаче слота: она может любить малое число очень удачных сделок.

Я бы сделал:

**Primary:** median `net exp_R` по OOS-folds.

**Constraints:**

* минимум `20` сделок на полном validation;
* не более `25%` ухудшения max DD относительно baseline;
* хотя бы `3 из 4` OOS-folds неотрицательны.

`PF`, Calmar, win-rate — только вторичные описательные метрики.

Для `mf-afternoon` из-за малой частоты допустил бы одно более длинное OOS-окно, но не стал бы искусственно дробить его на 3-месячные сегменты с 2–5 сделками.

---

## 3. Ограничить эффективное число параметров

Сейчас ORC фактически позволяет крутить много независимых ручек: `orbMinutes`, `breakoutThreshold`, ATR period/multiplier, reward ratio, trail activation, trail stages и т. д. Конфиг это показывает напрямую. 

Я бы ограничил research так:

**вход:** максимум 3 свободных параметра;

**выход:** максимум 3 свободных параметра;

всё остальное — fixed.

Например для ORC:

* `orb_minutes`
* `breakout_threshold`
* `atr_multiplier`

а `atr_period`, RR и trailing сначала фиксированы.

Затем отдельным проходом:

* `reward_ratio`
* `trail_activation_r`
* `trail_stage_max`

При этом не смешивать оба поиска.

Для `or-fade` аналогично: не давать одновременно свободно двигать `ORB`, `threshold`, `fadeWindow`, `tradeEnd`, ATR и выход.

Для `mf` — не более трёх из `lookback / threshold / SMA period / entry delay`, иначе при 46 сделках это почти гарантированная подгонка.

---

## 4. Учесть множественные сравнения — и не только среди шести слотов

Здесь проблема двойная:

1. сравниваются **6 слотов**;
2. внутри каждого — сотни trial'ов.

В текущем протоколе уже было `300 trials × 19 окон`. 

Поэтому простого «победил текущий champion на validation» недостаточно.

Я бы сделал так:

* заранее зарегистрировать все 6 primary tests;
* для финального утверждения слота контролировать family-wise error по этим 6 тестам, например **Holm correction**;
* выбор из сотен trial'ов делать только на train/inner-CV;
* final holdout не использовать для выбора вообще.

Для портфеля дополнительно смотреть **совместный** OOS прогон всех принятых слотов, потому что общий счёт и общий risk budget связывают их. В коде global risk — это общий бюджет открытого риска, а не шесть независимых депозитов.

# Что бы я сделал непосредственно перед следующим запуском

**Шаг 1:** сначала проверить ORC `close-entry` против `retest-limit` на том же наборе breakout-сигналов.

**Шаг 2:** `or-fade` не переподбирать, а провести frozen OOS; если снова degradation — удалить.

**Шаг 3:** `mf-afternoon` оставить фиксированным и добрать независимую выборку; сейчас оптимизировать его не стоит.

**Шаг 4:** только после этого переподбирать `orc-complement`, `wave2`, morning и evening — причём как проверку **двух входных механик**, а не только их численных параметров.

И ещё одно важное следствие прошлого ревью: **все live-результаты по этим шести слотам я бы пока не использовал как подтверждение стратегии**, пока не исправлен live same-bar trailing bug. Он особенно опасен потому, что backtest baseline при этом может выглядеть совершенно нормально.
