## Итог

Нашёл **пять подтверждённых кодом проблем/расхождений**, из них одна — прямое новое «заглядывание вперёд» в live. Ещё несколько слабых мест — именно пробелы тестов, а не обязательно ошибки продакшн-кода.

По влиянию на `exp_R` я бы поставил порядок так:

1. **Live-трейл закрывает позицию по close того же бара, которым этот же бар только что поднял стоп.**
2. **ORC-лимит в backtest/replay фактически восстанавливается задним числом из OHLC; биржевая задержка/очередь внутри бара отсутствует.**
3. **Приоритет слотов на одном тикере детерминирован в portfolio, но не детерминирован в live.**
4. **История стратегии зависит от того, была ли позиция открыта: `OnCandle` вообще не вызывается во время позиции.**
5. **В portfolio сброс global-risk происходит до `closeMissedEOD`, поэтому «зависшая через дыру» позиция закрывается уже после сброса дневного состояния.**

## 1. LIVE: новый трейл применяется и тут же проверяется по close того же бара

**Утверждение.** Это новое прямое нарушение правила «новый стоп действует со следующего бара». В live `trailOnBar` сначала передвигает стоп по экстремуму закрывшегося бара, а затем немедленно вызывает `checkSLTP` по `lastPrice`, которым перед этим в `Run` уже сделан `candle.Close`. В `runner.go` и `portfolio.go` после `trailing.Apply` такой проверки нет.   

**Файл:строка:** `internal/strategy/selfmanaged/selfmanaged.go:401, 408–410`

```go
trailing.Apply(s.pos, position.TrailPrice(candle, s.pos.Direction), s.cfg.TrailCfg)
stage, sl := s.pos.TrailStage, s.pos.StopLoss
s.mu.Unlock()
...
if last := s.currentLastPrice(); last > 0 {
	s.checkSLTP(ctx, sctx, last)
}
```

**Сценарий.** BUY: `Entry=100`, исходный `SL=99`, `R=1`. Пусть настройки те же, что уже зафиксированы в `intrabar_test.go`: `ActivationR=0.5`, `BreakevenR=0.05`; бар `O=100.2, H=100.8, L=99.9, C=100.0`. 

По модели backtest: исходный SL=99 на этом баре не задет; по закрытию `H=100.8` поднимает SL до `100.05`, и **позиция остаётся открытой**. Следующий бар, скажем, `O=99.5`, уже исполнит новый SL по `99.5`.

По live: `trailOnBar` поднимает SL до `100.05`, затем сразу сравнивает с `lastPrice=100.0` и закрывает **уже на текущем баре** по `100.0`.

При такой конструкции live получает примерно **+0.5R** против backtest в следующем баре. При другом следующем открытии разница может быть больше или меньше.

**Как проверить тестом.** Добавить тот же сценарий, но прогнать его через `SelfManagedStrategy.trailOnBar`, а не только через два backtest-драйвера: после бара с `H=100.8, C=100.0` позиция должна остаться открытой; только следующий бар должен иметь право исполнить новый стоп. Текущий `intrabar_test.go` этого не проверяет: там вообще нет `selfmanaged`. 

**Влияние на exp_R:** **высокое; уверен в механике, предполагаю в агрегированном масштабе**. Знак для этой конкретной ошибки — скорее вверх для live относительно baseline, потому что закрытие по текущему close вместо будущего open часто выгоднее, но величина зависит от следующего гэпа.

## 2. ORC: лимитная заявка исполняется из будущего OHLC, а не как реально живущая заявка

**Утверждение.** `OpeningRangeContinuation` действительно создаёт pending на баре пробоя, но фактический `Order` появляется только когда уже известен следующий закрывшийся бар и `fillPrice(candle)` посмотрел на его `Low/High/Open`. Это соответствует заданной бумажной модели, но создаёт систематическое расхождение с биржей: время, в которое заявка реально оказалась в очереди, и то, что произошло до момента её постановки/активации, не моделируются.  

**Файл:строка:** `internal/strategy/opening_range_continuation.go:201–206, 257–261`

```go
s.pending = &orcPendingLimit{
	direction:      direction,
	limitPrice:     entry,
	upper:          s.orbHigh,
	lower:          s.orbLow,
	placedAt:       candle.Timestamp,
```

и затем:

```go
p := s.pending
fill, filled := p.fillPrice(candle)
if !filled {
	return nil
}
```

**Сценарий.** Бар пробоя заканчивается в `10:00`, заявка BUY LIMIT 100 должна быть выставлена на close. Следующий бар: `O=100.5, H=101.0, L=99.8, C=100.2`. Код через OHLC говорит «лимит исполнился» и восстанавливает цену исполнения из этого бара. На бирже первый проход через 100 мог произойти сразу после 10:00 или почти мгновенно после выставления; могла быть очередь, неполученный timestamp, задержка отправки. Эти события код не различает.

**Как проверить тестом.** Не тестировать только `fillPrice()` как математическую функцию. Нужен сценарий из двух баров: breakout → следующий bar с единственным коротким касанием уровня. Тест должен отдельно зафиксировать, что текущая модель засчитывает fill, а затем сравнить baseline с более консервативной политикой «touch не гарантирует fill».

**Влияние на exp_R:** **высокое на частоту сделок, предполагаю на знак exp_R**. Текущая модель почти наверняка завышает вероятность исполнения лимита относительно реального рынка с очередью; знак изменения средней `exp_R` не обязан быть строго отрицательным, потому что исчезнут и победители, и проигравшие сделки.

## 3. Один тикер, несколько слотов: backtest детерминированно выбирает первый, live — гонку

**Утверждение.** Portfolio сортирует slot keys лексикографически и обрабатывает входы последовательно. В replay-тесте слоты также искусственно сортируются. Сам `SelfManagedStrategy` никакого общего приоритета между слотами не содержит; каждый экземпляр делает свой `TryOpen`, поэтому при одновременных сигналах победитель зависит от порядка выполнения горутин.

**Файл:строка:** `internal/backtest/portfolio.go:67–71`, `131–149`

```go
for k := range cfg.Tickers {
	slotKeys = append(slotKeys, k)
}
sort.Strings(slotKeys)
```

```go
for _, ev := range events[i:j] {
	p.processExits(ctx, executor, ev)
}
for _, ev := range events[i:j] {
	p.processEntries(ctx, executor, ev)
}
```

 

В replay порядок опять фиксируется:

```go
for tk := range byTicker {
	sl := byTicker[tk]
	sort.Slice(sl, func(i, j int) bool { return sl[i].cfg.Label < sl[j].cfg.Label })
}
```



**Сценарий.** На SBER в один `barEnd` одновременно дают сигнал `slot-A` и `slot-B`. `GlobalRisk` допускает одну позицию на тикер. В portfolio первым всегда выигрывает, например, `orc-complement/SBER`, если его ключ алфавитно раньше. В live первым может оказаться `mf-afternoon/SBER`. Если у этих стратегий разный `exp_R`, итоговый портфель меняется не из-за рынка, а из-за scheduler order.

**Как проверить тестом.** Два dummy-slot'а на одном тикере, один сигнал на одной и той же свече, `maxParallel=1`. Прогнать один и тот же набор при нескольких порядках запуска и потребовать один и тот же победивший слот по явно заданному priority field. Отдельно сравнить с portfolio.

**Влияние на exp_R:** **средне-высокое; уверен в расхождении, предполагаю в масштабе**. Если одновременные сигналы редки, эффект мал. Если часто конкурируют ORC/fade/MF на тех же бумагах, он может быть заметным. Для baseline это уже методологическая проблема воспроизводимости.

## 4. История стратегии эндогенна: во время позиции `OnCandle` вообще не вызывается

**Утверждение.** Сейчас состояние `CandleStrategy` обновляется только на свечах, когда слот flat. Причём проверка позиции стоит до `OnCandle`, а проверка времени — тоже до него. Это означает, что ATR/buffer/ORB и прочая внутренняя история перестаёт двигаться именно тогда, когда сделка открыта или когда слот вне окна.

**Файл:строка:** `internal/strategy/selfmanaged/selfmanaged.go:203–218`

```go
func (s *SelfManagedStrategy) processCandle(ctx context.Context, sctx contract.StrategyContext, candle models.Candle, now time.Time) {
	if ctx.Err() != nil || s.hasPos() {
		return
	}
...
	if !s.cfg.Session.EntriesAllowed(now) {
		return
	}
```



В backtest правило такое же: `EntriesAllowed(barEnd)` и `OnCandle` стоят внутри `processCandle`. 

**Сценарий.** Стратегия использует rolling history/ATR. На баре `t0` открылась позиция и она держится 10 баров. На `t1…t10` `OnCandle` не вызывается. На `t11` позиция закрылась, и только тогда стратегия получает новый бар. Её внутренняя история не равна истории рынка `t1…t10`. Следующий сигнал и расчёт стопа могут быть другими, чем у той же стратегии, которой дали все M5 подряд.

**Как проверить тестом.** Сделать strategy, которая возвращает сигнал, зависящий от счётчика `OnCandle` или последних N closes. Открыть позицию на первом баре и удерживать её 3–5 баров; после выхода проверить, какое число/окно увидела стратегия на следующем баре. Второй экземпляр той же стратегии должен получать все свечи и просто блокировать заявку — результаты состояния должны совпасть.

**Влияние на exp_R:** **среднее; уверен в механике, предполагаю по знаку**. Это не обязательно bias вверх/вниз, но baseline зависит от собственной торговой активности, что делает оценку стратегии нестационарной относительно рынка.

**Ответ на вопрос 4:** для stateful candle strategies — **да, лучше кормить всеми барами, а гейтить только заявку**. Иначе у стратегии появляется история «только тех баров, на которых мы не торговали».

## 5. Исправление дневного reset неполно для позиции, пережившей дыру

**Утверждение.** В portfolio `checkDailyReset` вызывается **до** `closeMissedEOD`. При этом `GlobalRisk.ResetDaily` очищает `openPositions`. Значит, если позиция реально пережила EOD из-за дыры в данных, её глобальный резерв риска исчезает до того, как stale-позиция будет закрыта.

**Файл:строка:** `internal/backtest/portfolio.go:191–200, 329–335`; `internal/engine/risk/global.go:181–190`

```go
for _, st := range slots {
	p.checkDailyReset(st, barEnd)
	if st.position != nil {
		p.closeMissedEOD(ctx, executor, st, candle)
	}
	if st.position != nil {
		p.processIntrabar(ctx, executor, st, candle)
```



А reset:

```go
today := st.session.Today(now)
if p.global != nil {
	p.global.ResetDaily(today)
}
```



И сам `ResetDaily`:

```go
g.realizedPnL = 0
g.openPositions = make(map[string]float64)
g.blocked = false
```



**Сценарий.** Позиция была открыта 1 сентября, последний бар до EOD есть, следующего вечернего бара нет, первый следующий доступный бар — 2 сентября. На первом баре 2 сентября portfolio сначала сбрасывает global risk, теряя запись об открытом риске 1 сентября, затем `closeMissedEOD` закрывает позицию по последнему close. PnL этого закрытия уже попадает в новый дневной `realizedPnL`.

Это не меняет сам `PnLR` закрытой сделки, но может изменить последующие `TryOpen`/circuit-breaker в новом дне.

**Как проверить тестом.** Нужен не только `TestMissedEODClosesAtLastClose`, а сценарий с реальным `GlobalRisk`: предыдущий день имеет открытую позицию и loss; следующий день первый бар вызывает reset + missed EOD; затем на том же/следующем баре проверяется возможность новой сделки и значение daily risk до/после stale close.

**Влияние на exp_R:** **низко-среднее; уверен в состоянии контроллера, предполагаю в агрегированном эффекте**. Это редкая ветка по данным, но она особенно неприятна тем, что может менять состав следующих сделок, а не только цену одной закрываемой сделки.

Live на закрытом баре делает `checkEOD` **до** `trailOnBar`, тогда как спецификация задаёт сначала путь → трейл → EOD.

s.checkDailyReset(now)

# Проверка тестов-стражей

## `intrabar_test.go`

Покрывается только один класс: **BUY + активация трейла + gap в следующем баре**, и только два backtest-пути (`runner`, `portfolio`). 

Он **не покрывает**:

* `SELL`;
* фиксированный SL/TP без трейла;
* одновременное касание SL и TP → должен победить SL;
* выход на `Open` по худшей из `Open` и SL;
* gap по `TP`;
* same-bar limit-fill → только SL;
* live `selfmanaged.trailOnBar`;
* главное найденное здесь: «trail по H/L → немедленная проверка по тому же Close».

Поэтому тест остаётся зелёным при сломанном live-трейле: он вообще туда не ходит.

---

## `session_time_test.go`

Покрыты три сценария, и оба backtest-пути: EOD на баре, ровно заканчивающемся EOD; missed EOD через gap; запрет входа на последнем EOD-баре. 

Пробелы:

* нет `SelfManagedStrategy`;
* нет `session_open_time + entry_delay`;
* нет перехода «бар разрешён/запрещён» на границе `session_open`;
* нет сценария с разными timezone/weekday filters;
* нет взаимодействия missed-EOD с `GlobalRisk`;
* нет проверки, что момент решения live и backtest используют **одинаковое время**.

Следовательно, тест останется зелёным, даже если live продолжит использовать `now`, а backtest — `barEnd`.

---

## `replay_history_test.go`

Это наиболее полезный guard, но у него три системных blind spot.

### 1. Он не вызывает `Run`

Тест вручную реализует свой порядок:

```go
s.checkEOD(ctx, sctx, c.Close, now)
s.trailOnBar(ctx, sctx, c)
s.processCandle(ctx, sctx, c, now)
```



Поэтому поломка именно orchestration внутри `SelfManagedStrategy.Run` может не проявиться.

### 2. Он сам фиксирует порядок слотов

Replay сортирует слоты по label. 

Это маскирует live race из пункта 3: replay проверяет детерминированный мир, а реальный live — нет.

### 3. Проверка цены выхода — по **среднему**, а не по каждой сделке

```go
if slipN > 0 && slipSum/float64(slipN) > 0.02 {
	t.Errorf("средняя разница выхода ...")
}
```



Это позволяет тесту оставаться зелёным при редкой, но большой ошибке. Например, одна ошибка `1.0R` на 1000 совпавших выходах даёт среднее всего `0.001R`; `max` только логируется и не проверяется.

**Именно поэтому найденный live-trail bug вполне может существовать и при зелёном `TestLiveMatchesBacktestOnHistory`.**

# Ответы на вопросы 1–6

### 1. Есть ли ещё зависимость решения от окончания этого же бара?

**Да.** Самая однозначная — `trailOnBar`: экстремум текущего бара поднимает стоп, затем этот же текущий `Close` используется как цена для `checkSLTP`. Это прямое same-bar lookahead.

Есть ещё потенциальная проблема в live с границей времени: `processCandle` проверяет `EntriesAllowed(now)`, а backtest — `EntriesAllowed(barEnd)`. В backtest это явно зафиксировано в спецификации и коде.  Если upstream вообще способен отдать «закрытую» свечу до фактического `barEnd`, live может принять решение по полному close ещё до конца бара. Сам факт такой ранней доставки из приложенного кода не доказан — см. «гипотезы» ниже.

### 2. Корректна ли схема «SL/TP фиксированы, трейл по close» для live?

**Как единая бумажная модель — да. Как точная модель реального тик-трейлинга — нет.**

Сильная сторона — теперь три пути действительно стараются считать одну и ту же дискретную модель: fixed SL/TP внутри бара, trailing after bar. Это прямо прописано в спецификации. 

Но это не эквивалент настоящему тик-трейлу. Реальный tick trail может двигать стоп раньше, чем закончится M5. Поэтому baseline после фиксации должен называться именно **bar-close trailing model**, а не «реальное live исполнение».

Главное: сначала исправить найденный same-bar `checkSLTP` — иначе live не реализует даже заявленную дискретную модель.

### 3. Как честно моделировать limit touch без тиков?

Текущая логика:

```go
if candle.Low > p.limitPrice {
	return 0, false
}
return math.Min(candle.Open, p.limitPrice), true
```



означает **100% fill при любом касании**.

Это верхняя граница по fill-rate, а не нейтральная оценка. Для OHLC невозможно восстановить очередь.

Я бы не вводил произвольное «N тиков» как единственную правду. Для baseline разумнее держать как минимум две полностью детерминированные границы:

* текущая `touch = fill`;
* консервативная `penetration = fill` только при проходе лимита хотя бы на 1 price step, сохраняя специальное правило `open < limit → fill at open`.

И смотреть `exp_R` **между двумя моделями**, а не выбирать одну псевдоточную вероятность.

### 4. Кормить стратегию всеми барами?

**Да.** Состояние стратегии и право выставить заявку — разные вещи. Сейчас они смешаны: наличие позиции физически удаляет свечи из истории стратегии. Код это делает до `OnCandle`. 

Для ORC/ATR-подобных стратегий это особенно существенно: rolling history должна отражать рынок, а не факт того, торговал ли слот в этот момент.

### 5. Нужен ли явный priority между слотами?

**Да, для воспроизводимого baseline нужен.**

Сейчас backtest использует alphabetic order, live — scheduling order. Это два разных execution policies. Случайность здесь не является свойством рынка; это свойство runtime.

Минимальное требование к модели: на одинаковом `barEnd` и одинаковом состоянии глобального риска выбор победителя должен быть воспроизводимым.

### 6. Что ещё расходится между paper и биржей у ORC?

Три конкретных вещи.

Во-первых, **очередь/касание** — уже рассмотрено выше.

Во-вторых, **latency постановки заявки на close breakout bar**: в коде pending создаётся на закрытии, а реальный `Order` появляется при анализе следующего OHLC-бара.  

В-третьих, **внутри следующего M5 нет временной информации о том, когда именно был первый проход лимита**. Поэтому «fill по open/limit» — это не биржевой timestamp исполнения, а восстановленная цена из агрегата.

# Гипотезы, не подтверждённые кодом

1. **Может ли `Candles()` реально прийти раньше `barEnd`?** В приложенном файле нет реализации feed/канала, поэтому отсутствие проверки `now >= barEnd` подтверждено, а вероятность ранней доставки — нет.

2. **Насколько часто live slot-order действительно различается на практике?** Код подтверждает отсутствие явного приоритета и детерминированность backtest, но частота конкретных гонок зависит от runtime orchestration, которого в пакете нет.
