# Часть 1. Модель исполнения

**Главная новая находка: во всех трёх путях лимитный фил может ошибочно превратиться во «вход по close» и избежать стопа, пробитого в баре фила.** Есть также проблема причинности при распределении портфельных ресурсов: лимитные исполнения внутри бара обслуживаются ресурсами, освободившимися позднее в этом же баре.

Ниже — статический разбор приложенного пакета. Номера строк относятся к дампу. Историю и Go-тесты я не запускал: фактическое число затронутых сделок и пересчитанный exp_R здесь не установлены.

Находки отсортированы прежде всего по потенциальному влиянию на **исторический exp_R**. Последние две относятся к live и непосредственно текущий baseline не меняют. В численных сценариях slippage отключён для прозрачности; R указан до комиссии, если не оговорено иное.

## 1.1. Новые находки

### 1. Лимитный фил, случайно совпавший с close, избегает same-bar стопа

**Утверждение.** Способ входа определяется равенством цен, а не происхождением заявки. Если лимит исполнился внутри бара и бар закрылся ровно по цене фила, код объявляет вход совершённым на закрытии. Это **неполное исправление same-bar модели**, общее для трёх путей.

**Код:**

`internal/backtest/portfolio.go:249`:

```go
entryAtClose := signal.Price == candle.Close
```

`internal/backtest/runner.go:190`:

```go
entryAtClose := signal.Price == candle.Close
```

`internal/strategy/selfmanaged/selfmanaged.go:240`:

```go
entryAtClose := signal.Price == candle.Close
```

После переноса этого значения в позицию срабатывает `internal/engine/position/position.go:211–214`:

```go
// Вход по цене закрытия бара — same-bar OHLC до entry не применяем.
if pos.EntryAtBarClose {
	return ""
}
```

**Сценарий.**

- Стоит BUY-лимит 100, SL = 99.70.
- TP = 100.3675746 — примерно `1.225248681R`, как у `orc-complement`.
- Бар фила: **O=100.20, H=100.40, L=99.60, C=100.00**.
- Правильный результат: лимит исполнился на снижении через 100, затем стоп 99.70: **−1R**.
- Код: `signal.Price == candle.Close`, поэтому same-bar стоп пропущен.
- Следующий бар: **O=100.00, H=100.50, L=99.90, C=100.40**. Позиция закрывается по TP: **+1.225R**.

Разница — примерно **+2.225R на одной сделке**. Проверка SL/TP по close в live здесь не спасает: close=100 находится между SL и TP.

**Как проверить тестом.**

Один и тот же pending BUY провести через `portfolio`, `runner`, `selfmanaged`:

1. При C=100 ожидать same-bar SL.
2. Повторить с C=100.001 — результат должен остаться SL.
3. Зеркально проверить SELL.
4. Отдельный настоящий close-вход при тех же OHLC должен **не** получать этот исторический стоп.

Исправление — явный тип/момент исполнения в сигнале: например, `EntryAtBarClose`, заданный стратегией либо исполнителем, а не восстановленный сравнением цен.

**Влияние на exp_R.**

- **Уверен:** конкретный сценарий завышает результат; ошибка действительно зависит от того, чем закончился бар.
- **Предполагаю:** это наиболее опасный из найденных остаточных источников оптимизма ORC. Частота неизвестна.
- При неизменных остальных сделках **23 таких подмены** дали бы около `23 × 2.225 / 1534 ≈ 0.033R` — весь нынешний плюс портфеля. Это оценка масштаба, не утверждение о наличии 23 случаев.

### 2. Портфель финансирует прошлый лимитный фил будущим выходом того же бара

**Утверждение.** Двухпроходная обработка правильна для входов по close, но применяется и к ретроспективным лимитным филам. В результате заявка, исполнившаяся на open или раньше другого выхода, получает кэш, свободный тикер и риск-бюджет **после** этого выхода.

Здесь есть противоречие внутри спецификации: пункт 6 описывает порядок close-входов, а пункт 7 требует реально существующую внутрибараную заявку.

**Код — `internal/backtest/portfolio.go:145–150`:**

```go
for _, ev := range events[i:j] {
	p.processExits(ctx, executor, ev)
}
```

```go
for _, ev := range events[i:j] {
	p.processEntries(ctx, executor, ev)
}
```

Кэш проверяется уже во втором проходе, `portfolio.go:258–260`:

```go
if bal, err := executor.GetBalance(ctx); err == nil {
	cashAtOpen = bal
	qty = st.cfg.capQuantityByCash(qty, fillPrice, bal)
```

Но цена такого «нового» входа может относиться к open, `opening_range_continuation.go:98–101`:

```go
if candle.Low > p.limitPrice {
	return 0, false
}
return math.Min(candle.Open, p.limitPrice), true
```

**Сценарий.**

- Перед 11:00 весь доступный кэш занят позицией B.
- У A в стратегии есть pending BUY 100. Ресурсы под pending не резервировались.
- Бар A: **O=100, H=100.20, L=99.90, C=100.10**. Лимит считается исполненным сразу на open.
- Бар B: **O=100, H=100.60, L=99.90, C=100.50**, существующий TP=100.50. На open позиция B ещё открыта; деньги освободятся позже.
- Портфель сначала закрывает B, затем покупает A по **прошлой цене 100** на освободившиеся деньги.

При реальном обеспеченном размещении полная заявка A не могла существовать с таким объёмом. Выставить её после выхода B — другая сделка: касание 100 уже могло закончиться.

Обратная сторона: убыток B позднее внутри бара может включить CB и задним числом удалить фил A, который случился раньше.

**Сверка трёх путей.**

- `portfolio.go` содержит именно общий двухпроходный механизм.
- `runner.go:178–214` тоже определяет объём только при выдаче исторического фила, но межтикерной конкуренции в нём нет: такой эффект одиночным прогоном не воспроизводится.
- В live `selfmanaged.go:253–285` кэш и `TryOpen` проверяются при обработке закрытого бара, после внутренних движений цены. Поэтому бумажный live может разделять эту ошибку с портфельным backtest.

**Как проверить тестом.**

Двухтикерный сценарий выше с настоящим учётом баланса:

- зафиксировать нулевой свободный кэш перед open;
- обеспечить выход B только после open;
- проверить, что A не получает ретроспективно профинансированный фил;
- повторить с двумя слотами одного тикера: раннее касание pending и поздний выход старой позиции.

Для исполняемой модели нужны состояние заявки, заранее определённый объём и резервирование ресурсов при размещении. Для неоднозначного межтикерного порядка внутри M5 — заранее заданное консервативное правило, а не использование всех будущих выходов.

**Влияние на exp_R.**

- **Уверен:** причинность и состав доступных сделок нарушаются.
- **Предполагаю:** влияние может быть существенным из-за общего кэша; знак не установлен. Ошибка способна как добавлять сделки, так и удалять их через CB.
- Число `ticker_busy_skips=94` этот эффект не измеряет: ретроспективно разрешённые исполнения в skips не попадут.

### 3. Гейт последнего бара удаляет уже стоявшие лимиты вместе с новыми close-входами

**Утверждение.** Исправление запрета новых входов на `barEnd == EOD` слишком широкое: стратегия вообще не вызывается. Поэтому pending, законно существовавший **внутри последнего бара**, не исполняется.

Это не повтор известного запрета входить по close в EOD. Проблема — различие между **новым решением на закрытии** и **исполнением старого решения до закрытия**.

**Код — `internal/backtest/portfolio.go:230–233`:**

```go
func (p *PortfolioRunner) processCandle(ctx context.Context, executor contract.OrderExecutor, st *tickerState, candle models.Candle, barEnd time.Time) {
	if !st.session.EntriesAllowed(barEnd) {
		return
	}
```

То же: `runner.go:170–173`, `selfmanaged.go:217–219`.

При этом pending сам по себе ещё не истёк, `opening_range_continuation.go:248–251`:

```go
if !candle.Timestamp.Before(s.pending.expiresAt) {
	s.pending = nil
	return nil
}
```

**Сценарий.**

- Утренняя сессия, EOD=09:50.
- На закрытии бара 09:40–09:45 поставлен BUY-лимит 100, SL=99.70. Срок — до 10:00.
- Последний бар 09:45–09:50: **O=100.20, H=100.30, L=99.60, C=99.65**.
- Реальная заявка исполнилась и получила SL: **−1R**.
- Во всех трёх путях `EntriesAllowed(09:50)` возвращает false до `OnCandle`. Сделки нет.

Если вместо этого L=99.90 и C=100.10, правильная модель должна исполнить лимит и закрыть оставшуюся позицию в EOD, а не удалить сделку.

**Как проверить тестом.**

Предзаданный pending плюс последний бар:

1. Касание лимита и стопа — одна убыточная сделка.
2. Касание лимита без стопа — вход и EOD по close.
3. Новый close-сигнал на этом же баре — запрещён.
4. Нет касания — нет сделки.

Обработку существующих заявок нужно отделить от разрешения создавать новые. Просто убрать `EntriesAllowed` нельзя.

**Влияние на exp_R.**

- **Уверен:** приведённый убыток пропускается; три пути совпадают в ошибке.
- **Предполагаю:** общий знак зависит от доходности пропущенных последних ретестов. Частота и итоговый эффект неизвестны.
- Затрагивает ORC, а не настоящие close-входы or-fade/MF.

### 4. `closeMissedEOD` не завершает позиции, если больше нет бара именно этого тикера

**Утверждение.** Страховка работает лишь при следующем событии по соответствующему тикеру. Остаточная позиция на конце массива не экспортируется в сделки и не учитывается в exp_R.

**Код — конец `internal/backtest/runner.go:150–153`:**

```go
	r.lastClose, r.lastBarEnd = candle.Close, barEnd
}
return nil
```

В портфеле аналогично заканчивается `Run`, `portfolio.go:151–154`:

```go
	i = j
}
return nil
```

А статистика берётся из закрытых сделок, `internal/optimizer/eval/portfolio_backtest.go:176–179`:

```go
trades := store.Trades()
metrics := AggregateTrades(trades, costsCfg, cfg.ClassCode)
expR, expRub, pf := detailedTradeStats(trades, costsCfg, cfg.ClassCode)
byExp := statsByExperiment(trades, costsCfg, cfg.ClassCode)
```

**Сценарий.**

- Вечерняя позиция: BUY 100, SL=99.70, TP=100.60.
- Последний имеющийся бар её тикера — 23:25: **O=100, H=100.05, L=99.85, C=99.90**.
- Баров этого тикера дальше нет. У других тикеров портфель доходит до 23:50.
- Код оставляет позицию открытой; в `store.Trades()` её нет.
- Согласно вашей модели EOD по последней известной цене, результат должен быть около **−0.333R**.

Для массива, сознательно обрезанного посреди дня, принудительное закрытие по прошлой цене не обязательно правильно. Но тогда нужно явно показать открытую экспозицию и её оценку, а не выдавать только closed-trade exp_R как результат всего периода.

**Как проверить тестом.**

Взять `TestMissedEODClosesAtLastClose`, убрать следующий утренний бар:

- для портфеля оставить событие другого тикера на EOD;
- задать явный горизонт расчёта;
- проверить отсутствие неучтённой позиции и наличие результата EOD либо явно отражённого остатка.

**Влияние на exp_R.**

- **Уверен:** крайняя открытая позиция может быть исключена из статистики.
- **Предполагаю:** на полном массиве эффект обычно меньше первых трёх находок; знак зависит от исключённых позиций.
- Это также важно при сравнении коротких окон оптимизации: границы создаются многократно.

### 5. После неудачного EOD-закрытия live считает EOD завершённым и не повторяет его

**Утверждение.** Транзиентная ошибка закрытия восстанавливает позицию, но `checkEOD` безусловно записывает, что EOD уже выполнен. Комментарий о повторе на следующем тике для этого случая неверен.

**Код — `internal/strategy/selfmanaged/selfmanaged.go:425–428`:**

```go
if s.hasPos() {
	s.closePosition(ctx, sctx, price, models.CloseReasonEOD)
}
s.eodCloseDate = today
```

Восстановление после ошибки, `selfmanaged.go:486–489`:

```go
s.mu.Lock()
s.pos = pos
s.mu.Unlock()
return
```

Последующие попытки блокирует `selfmanaged.go:421–424`:

```go
today := s.cfg.Session.Today(now)
if s.eodCloseDate == today {
	return
}
```

**Сценарий.**

- BUY 100, SL=99.70, TP=100.60.
- Бар 18:35–18:40: **O=100, H=100.10, L=99.90, C=100**.
- Первый EOD-ордер возвращает транзиентную ошибку.
- Позиция восстановлена, `eodCloseDate` установлен.
- Следующий тик 100.05 не вызывает ни SL, ни TP; повторного EOD нет.
- Позиция может пережить ночь. Следующее открытие 99 вместо закрытия около 100 даёт примерно **−3.33R** до издержек.

**Как проверить тестом.**

Executor, который:

1. Первый EOD-close отклоняет.
2. Второй принимает.

Дважды вызвать `checkEOD` в одну дату с ценами внутри SL/TP. Ожидать две попытки и закрытую позицию. Сейчас вторая попытка не произойдёт.

Признак завершённого EOD должен зависеть от результата закрытия, например от подтверждённого отсутствия позиции.

**Влияние на exp_R.**

- **Уверен:** ошибка воспроизводится при указанном ответе исполнителя.
- **Уверен:** текущий исторический baseline без ошибок исполнителя она не меняет.
- **Предполагаю:** для live это редкий, но потенциально большой хвост убытков; частоты ошибок в пакете нет.

### 6. Повторная свеча может применить к новой позиции экстремум, случившийся до входа

**Утверждение.** Утверждение в комментарии, что бар входа не попадёт в `trailOnBar`, верно только при однократной упорядоченной доставке свечей. Дубликат сначала проходит управление позицией и лишь затем попадает в защиту от дубликатов стратегии.

**Код — `internal/strategy/selfmanaged/selfmanaged.go:184–188`:**

```go
s.setLastPrice(candle.Close)
s.checkDailyReset(now)
s.checkEOD(ctx, sctx, candle.Close, now)
s.trailOnBar(ctx, sctx, candle)
s.processCandle(ctx, sctx, candle, now)
```

Внутри трейла нет проверки времени входа, `selfmanaged.go:399–401`:

```go
position.UpdateMFE(s.pos, position.TrailPrice(candle, s.pos.Direction))
prevStage := s.pos.TrailStage
trailing.Apply(s.pos, position.TrailPrice(candle, s.pos.Direction), s.cfg.TrailCfg)
```

**Сценарий.**

- Приходит закрытый бар **O=100, H=101, L=99.80, C=100**.
- На close открывается BUY 100, SL=99.70, TP отключён.
- Для теста: activation=0.5R, stageMax=1.
- До нового тика приходит дубликат той же свечи.
- `trailOnBar` использует прежний H=101. Непрерывная стадия может поднять SL до `101−0.30=100.70`.
- Проверка текущего close=100 закрывает позицию, хотя **после её открытия не было движения к 101**.

Для чистой проверки взять signal-stub, который выдаёт close-вход: здесь проверяется адаптер, не способность конкретной стратегии породить такой сигнал.

**Как проверить тестом.**

Дважды доставить одну свечу в live-последовательности. После второго сообщения должны сохраниться:

- исходный SL;
- исходная стадия трейла;
- MFE, не включающий до-входовой high;
- открытая позиция.

Заодно проверить доставку старой свечи после открытия на более новой. Проверка свежести только внутри `processCandle` этого не защищает.

**Влияние на exp_R.**

- **Уверен:** при указанной последовательности код использует до-входовой экстремум.
- **Предполагаю:** реальная частота зависит от фида и реконнектов, которых в пакете нет; знак влияния на доходность не определён.
- На обычном историческом прогоне без дубликатов эффект нулевой.

## 1.2. Что именно не держат тесты-стражи

### А. Все три стража могут остаться зелёными при поломке лимитного входа только в `runner.go`

**Код.**

`intrabar_test.go:44–46` вызывает непосредственно обработку уже открытой позиции:

```go
"runner": {
	process: func(c models.Candle) { r.processIntrabar(ctx, nopExecutor{}, c) },
	pos:     func() *position.State { return r.position },
```

`session_time_test.go:23–24` создаёт только close-вход:

```go
s.done = true
return &models.Order{Direction: "BUY", Price: c.Close, StopLoss: c.Close * 0.9, TakeProfit: c.Close * 1.1}
```

`replay_history_test.go:186` сравнивает live только с портфелем:

```go
bt, err := eval.RunPortfolioBacktest(ctx, eval.PortfolioBacktestOptions{ConfigPath: cfgPath, HistoryDir: hist, SlippageBps: -1})
```

**Сценарий поломки.** Удалить из `runner.processCandle` вызов `SameBarExitAfterFill`. BUY-лимит 100 на баре O=100.20, H=100.30, L=99.60, C=99.80 при SL=99.70 останется жив вместо −1R.

**Почему зелёное возможно.** Intrabar-тест не проходит вход; session-тесты входят по close; history-replay не вызывает одиночный Runner.

**Точный тест.** Один общий набор сценариев исполнения сигнала прогнать через все три адаптера, включая лимитный вход, same-bar SL, EOD pending и явный close-вход.

**Влияние:** **уверен**, стражи не обеспечивают заявленную полную сверку трёх путей; потенциальное искажение exp_R — вплоть до эффекта находки 1. Это пробел защиты, а не дополнительное установленное искажение baseline.

### Б. Intrabar-страж не защищает SELL и приоритет стопа при касании обоих уровней

**Код — `intrabar_test.go:65–68`:**

```go
return &position.State{
	Direction: "BUY", Quantity: 10, EntryPrice: 100, RDistance: 1,
	StopLoss: 99, InitialStopLoss: 99, TakeProfit: 103, InitialTakeProfit: 103,
	MFEPrice: 100, MAEPrice: 100, OpenedAt: t0,
```

В его первом баре H=100.8 — до TP=103 далеко.

**Сценарии, которые он не проверяет:**

- BUY 100, SL=99.70, TP=100.60; **O=100, H=100.70, L=99.60, C=100** → должен быть SL.
- SELL 100, SL=100.30, TP=99.40; **O=100.50, H=100.60, L=99.30, C=99.50** → стоп по open 100.50.
- Зеркальный SELL-трейл с гэпом через новый стоп.

Замена порядка BUY-экстремумов на favorable-first может оставить этот тест зелёным, хотя первый сценарий превратится из −1R в +2R.

**Точный тест:** таблица BUY/SELL × open-gap/no-gap × SL/TP/both, отдельно от таблицы трейла.

**Влияние:** **уверен**, локальная мутация может менять результат на несколько R на сделку и не обнаруживаться этим стражем. Исторический replay может её поймать, но только если соответствующий сценарий встретился в истории и тест был включён.

### В. Session-стражи проверяют запрет нового close-входа, но не жизнь pending и не неудачу EOD

**Код — `session_time_test.go:122–124`:**

if open || len(store.Trades()) != 0 {
	t.Fatal("бар 09:45–09:50 при eod 09:50 не должен давать вход")

**Непокрытые сценарии:** находки 3–5 — старый pending в последнем баре, отсутствие следующего собственного бара, ошибка первого EOD-close.

**Как проверить:** добавить именно три описанных сценария, сохранив существующий запрет нового close-входа.

**Влияние:** **уверен**, тест может быть зелёным при каждой из этих поломок; величина эффекта — как в соответствующих находках.

### Г. Replay не сравнивает цену входа, объём и геометрию риска

Это **дополнительно** к уже известному слабому ограничению на разницу выходов.

**Код — `replay_history_test.go:190–192`:**

```go
key := func(tr models.ClosedTrade) string {
	return fmt.Sprintf("%s|%s|%s|%s", tr.ExperimentID, tr.Ticker, tr.Direction, tr.EntryBarTime)
}
```

Цена входа, Quantity, InitialSL и RDistance не участвуют в ключе. Итоговые assertions в строках 267–276 требуют совпадения ключей, причин и средней разницы выходов.

**Сценарий.**

- Одинаковые ключ, SL=99.70, TP=100.60, причина TP, ExitPrice=100.60.
- В одном пути EntryPrice=100, R=0.30 → прибыль **2R**.
- В другом EntryPrice=100.10, R=0.40 → прибыль **1.25R**.
- Следующий бар O=100.20, H=100.70, L=100.15, C=100.60; трейл недостижим.

Проверка цены выхода ничего не обнаружит. Аналогично Quantity=10 вместо 100 может пройти сверку, хотя рублёвый результат различается в десять раз.

**Как проверить.** На изолированном наборе без конкуренции за кэш намеренно исказить только EntryPrice, затем Quantity. Assertions должны падать отдельно на:

- EntryPrice;
- Quantity;
- InitialSL/TP;
- RDistance;
- net PnL, приведённом к одной модели комиссии;
- остаточных открытых позициях.

**Влияние:** **уверен**, совпадение текущих проверяемых полей не означает совпадения exp_R или рублёвого результата.

Кроме того, replay вызывает методы напрямую и подаёт каждую свечу один раз. Он не проверяет `Run` с его каналами, таймером, дубликатами и ошибками исполнения — поэтому находки 5–6 с ним совместимы.

## 1.3. Ответы на вопросы 1–6 раздела 8

### Вопрос 1. Осталось ли заглядывание внутрь бара?

**Да:**

1. Определение типа входа по совпадению с итоговым close — находка 1.
2. Использование ресурсов после всех будущих выходов для более раннего лимитного фила — находка 2.
3. При повторной доставке свечи — использование до-входового экстремума для новой live-позиции, находка 6.

**Дополнительного look-ahead в расчёте ATR для обычного ORC-фила не нашёл.** В `tryFillPending` SL/TP считаются по уже накопленному `s.buffer.history`; текущий бар фила перед этим не добавляется. У MF/or-fade текущий закрытый бар входит в ATR, но решение у них принимается по close — само по себе это допустимо.

В `IntrabarPath` и базовом переносе трейла сверх перечисленных вами известных различий нового оптимистичного порядка экстремумов не нашёл.

### Вопрос 2. Корректен ли баровый трейл как модель live?

**Да, если live действительно торгует именно эту политику.** Сейчас `checkSLTP` не двигает трейл, а `trailOnBar` пересчитывает его по закрытой свече. Это самостоятельная исполняемая стратегия, а не приближение тикового трейла.

Не следует утверждать, что она воспроизводит тиковый трейл: это другой выход. Но менять live под заранее определённую баровую политику корректно.

Нужно точно определить момент вступления нового стопа в силу и устранить уже известное расхождение close/следующий open. До-входовые и повторные свечи применять к трейлу нельзя.

### Вопрос 3. Как моделировать лимит без очереди и тиков?

**Из ваших OHLCV нельзя оценить вероятность исполнения по касанию.** Общий объём бара не сообщает ни объём на конкретной цене, ни очередь перед заявкой.

Для существующей ORC-диагностики я бы фиксировал до прогона:

- основной вариант — нынешнее касание, явно как оптимистичный сценарий;
- стресс — проход уровня на 1, 2 и 3 б.п.;
- отдельную обработку открытия за лимитом;
- количество исчезнувших сделок и их результаты в исходной модели.

Это **анализ чувствительности**, не калиброванная модель биржи. Нельзя выбрать глубину прохода, которая лучше совпала с желаемым exp_R.

Проход на N тиков требует таблицы реального шага цены. Вероятностный фил «по объёму бара» без наблюдений исполнения добавит выдуманные параметры и не улучшит достоверность.

### Вопрос 4. Кормить ли стратегию всеми барами?

**Да — отделить обновление состояния рынка от разрешения заявок.**

Но просто убрать внешний `EntriesAllowed` недостаточно: тогда текущий `OnCandle` начнёт создавать pending/watch и отмечать сигналы в моменты, когда торговать нельзя.

Нужны отдельно:

1. Обновление истории и индикаторов каждым закрытым баром выбранной торговой сессии.
2. Обновление OR/watch по явно заданному окну.
3. Разрешение создать заявку.
4. Жизненный цикл уже созданной заявки.

Для MF это **новая версия стратегии**. Её результат нельзя считать подтверждением старых 46 сделок: вы исправляете сам объект, на котором определялись канал и ATR.

### Вопрос 5. Нужен ли явный приоритет слотов?

**Да, нужен детерминированный арбитраж заявок на общем счёте.** Не потому, что 94 skips автоматически велики, а потому, что запас доходности очень мал.

Иллюстрация масштаба: если у 94 конфликтов разница между победившим и проигравшим сигналами в среднем 0.5R, это `94×0.5/1534≈0.031R`. Это не оценка ваших конфликтов, но почти весь нынешний exp_R.

Проверка:

- зафиксировать один нейтральный приоритет до расчёта;
- отдельно выполнить обратный порядок и заранее заданные, например 100, перестановок;
- сравнивать распределение **net PnL и exp_R всего портфеля**, не выбирать лучшую перестановку;
- восстановить альтернативные сигналы в точках конфликтов.

Приоритет должен работать вместе с резервированием pending из находки 2. Иначе порядок close-сообщений всё равно будет распределять ресурсы задним числом.

### Вопрос 6. Что ещё расходится между бумагой и биржей?

Помимо известной ретроспективной постановки ORC:

- обеспечение и объём заявки должны существовать до фила — находка 2;
- исполнение pending нельзя отменять запретом новых close-входов в EOD — находка 3;
- неудачное EOD-закрытие должно повторяться — находка 5;
- доставка повторной свечи не должна менять позицию на основании её до-входовой истории — находка 6.

**Гипотезы, не подтверждённые кодом пакета:**

- `ExecuteOrder == nil` в реальном брокерском адаптере может означать принятие заявки, а не полное исполнение; код адаптера не приложен.
- Комиссия может по-разному уменьшать доступный кэш в backtest и live. В backtest-close нет заполнения `CommissionRub`, в live оно есть, но без реализации executor полный эффект на баланс не доказан.
- Не проверены частичные исполнения, округление к биржевому лоту/шагу цены и доступность шорта.
- Не установлена частота задержанных и повторных свечей.

Эти пункты не включаю в доказанные находки и не приписываю им численное влияние на baseline.

3. Основное сравнение ядра и дополнительных бумаг вести на общем доступном периоде до 2026-07-12. Хвост ядра до 2026-10-02 показывать отдельно.
4. Ресемплировать целые торговые даты/недели одновременно по всем тикерам. Сделки одного рыночного события не считать независимыми.
5. Базовая стоимость — 3.6 б.п.; обязательный стресс — 5.6 б.п., соответствующий 2 б.п. на ногу плюс комиссия.
6. Недостаточную выборку отличать от отрицательного результата: **оба не разрешают признать преимущество**, но причины разные.

### План для or-fade

**Первичная проверка:** точная замороженная текущая логика, включая скользящее окно watch и `require_inside_range=false`.

**Заранее заданные срезы:**

- исходные четыре тикера;
- остальные шесть тикеров ядра;
- все 15 дополнительных;
- BUY и SELL;
- первая и вторая сделка тикера за день;
- будни и выходные отдельно;
- шесть последовательных временных блоков;
- группы волатильности, определённые по информации до входа, с границами по прошлой истории, а не по будущей доходности.

Временные блоки можно зафиксировать так:

1. 2024-07–2024-12;
2. 2025-01–2025-04;
3. 2025-05–2025-08;
4. 2025-09–2025-12;
5. 2026-01–2026-04;
6. 2026-05–конец доступной истории.

**Минимум для содержательного решения:**

- ≥400 сделок суммарно;
- из них ≥200 на дополнительных 15 тикерах;
- ≥120 различных торговых дат;
- временной срез интерпретировать отдельно только при ≥30 сделках.

Это минимальные рабочие пороги, не гарантия мощности. При σ≈1R для обнаружения истинного +0.15R с 80% мощностью и поправкой на шесть гипотез потребуется порядка **466 независимых наблюдений**; кластеризация увеличивает требование.

**Что будет означать «не верить»:**

- при достаточной выборке дополнительные 15 дают net exp_R≤0 даже при 3.6 б.п.;
- объединённый результат при 5.6 б.п. неположителен;
- удаление одного тикера или одного временного блока делает совокупный результат отрицательным;
- преимущество сосредоточено в одном направлении/режиме, а это разделение не было исходной гипотезой;
- после поправки на множественные проверки нижняя граница доверительного интервала не выше нуля — тогда преимущество **не подтверждено**, даже если точечная оценка положительна.

Не требовал бы значимости в каждом малом срезе: это почти гарантированно отбракует и рабочий слабый эффект. Проверять нужно переносимость и концентрацию, а не коллекцию p-value.

### План для MF

Разделить два разных объекта:

1. **Текущий MF с разорванной историей** — замороженный диагностический прогон.
2. **MF с непрерывной историей** — новая зарегистрированная гипотеза. Старые +0.261R на 46 сделках ей не приписывать.

Для текущей версии заранее разбить сделки по:

- доле предыдущего дня в канале на входе;
- входам вскоре после допуска к торговле и позже;
- MGNT/TATN и всем остальным бумагам;
- временным блокам;
- размеру движения относительно вчерашней цены, чтобы отделить перенос уровня через ночь от внутридневного импульса.

**Минимум:** ≥300 сделок, ≥200 вне MGNT/TATN, ≥100 дат. Если правила не дают столько событий, не расширять параметры ради набора статистики.

**Контроль:** сравнить с long-входами в тех же тикерах, времени дня и сопоставимом заранее известном уровне волатильности, но без breakout-сигнала. Это проверяет добавочную ценность именно пробоя, а не благоприятные часы/бумаги для long.

**«Не верить»:**

- на остальных бумагах net exp_R≤0;
- нет положительной добавочной доходности к такому time/volatility-контролю;
- знак держится только на входах с преимущественно вчерашним каналом, хотя гипотеза заявлена как внутридневная;
- стресс 5.6 б.п. убирает преимущество;
- выборка остаётся ниже минимума.

При нынешних 46 сделках поиск новых параметров скорее увеличит число объяснений задним числом, чем уверенность.

## 2.3. Вопрос 10: что изменить до следующего подбора

### 1. Разбиение: вложенное и блочное, без заявления о новом «чистом хвосте»

Для будущего ограниченного поиска:

- использовать шесть фиксированных временных блоков выше;
- первые два — начальное обучение;
- затем четыре последовательных проверки: выбор только по прошлым блокам, оценка на следующем;
- внутри обучения — отдельные последовательные внутренние разбиения;
- дополнительно пять фиксированных групп тикеров, определённых до результатов, для проверки переноса на исключённую группу.

Не перемешивать отдельные сделки случайно: это разносит один рыночный режим и одно событие по train/test.

Историю для индикаторов переносить причинно, но сделки, пересекающие границу оценки, не включать одновременно в обе части. Обработка warm-up должна быть одинаковой у кандидатов.

**Оговорка существенная:** это оценка устойчивости процедуры на уже известной истории, а не восстановленный независимый эксперимент.

### 2. Основная метрика: нижняя граница net exp_R при стресс-издержках

Вместо медианы Calmar на перекрывающихся двухмесячных окнах:

- первичная метрика — pooled net exp_R на внешних блоках при 2 б.п. slippage на ногу;
- ранжирование — по нижней односторонней доверительной границе, рассчитанной недельными блоками;
- число сделок и дат — обязательный фильтр;
- рублёвый net PnL и просадка — ограничения и экономическая проверка.

Почему недостаточно одного exp_R: в `portfolio_backtest.go:207–210` каждая сделка нормируется на свой фактический риск:

```go
riskAmt := t.RDistance * float64(t.Quantity) * step
if riskAmt > 0 {
	sumR += net / riskAmt
```

Сделка, сильно урезанная кэшем, может иметь тот же вес в среднем R, что и полноразмерная. Для общего счёта нужно дополнительно проверять **добавочный рублёвый результат на торговую дату**.

### 3. Не более трёх подбираемых параметров на семейство

Конкретный бюджет:

- ≤3 активных параметров;
- ≤3 заранее заданных значения каждого;
- ≤27 конфигураций плюс замороженный baseline;
- все временные значения кратны M5;
- тикерный whitelist не является дополнительной ручкой поиска;
- неработающие фильтры и недостижимые стадии исключаются из пространства, а не «оптимизируются».

Индикаторные периоды, окно торговли и модель выхода фиксируются по гипотезе до поиска. Если они тоже перебираются, они входят в тот же бюджет, а не считаются бесплатными.

### 4. Множественные сравнения: шесть слотов — это минимум, не всё число попыток

Для шести заранее заявленных финальных гипотез:

- Holm с семейной ошибкой 5%, либо синхронный block-bootstrap max-statistic;
- при простом Bonferroni первичный односторонний уровень — `0.05/6≈0.00833`.

Но поправка на шесть **не покрывает** сотни просмотренных конфигураций. Их выбор должен находиться внутри вложенной процедуры. Если ранжирование делается по тем же данным, на которых строится bootstrap, нужно повторять **весь выбор победителя** внутри ресемплирования, а не ресемплировать только его сделки.

Неизвестное число старых человеческих и оптимизаторных попыток задним числом надёжно не исправить. Старые результаты остаются exploratory.

### 5. Портфельная проверка — по добавочной полезности, с замороженным арбитражем

Каждый финалист:

1. Отдельно.
2. В составе заранее зафиксированного базового портфеля.
3. С тем же приоритетом заявок и моделью резервирования.
4. С отчётом: какие сделки он вытеснил, сколько кэша забрал, как изменил net PnL по датам.

Не принимать слот только потому, что у него положительный standalone exp_R: на общем счёте он может вытеснять лучшие сделки.

# Часть 3. Новые стратегии

## 3.1. Что действительно следует из вашей картины

Ваши проверки достаточно убедительно говорят: **покупать недавний короткий импульс в расчёте на ещё несколько M5-баров — плохое базовое направление поиска**.

Они не устанавливают, кто именно создаёт движения. Из OHLCV нельзя доказать, что это стопы розницы, фондовый поток или ликвидация плечей.

Поэтому следующие три идеи — **гипотезы, не подтверждённые кодом или вашими прогонами**. Они привязаны к смене ликвидности, времени сворачивания внутридневной экспозиции и календарному потоку. Ни для одной я не утверждаю положительное ожидание.

### Общая модель дешёвой проверки

- Все часы ниже — **МСК**; CSV с UTC сначала конвертировать.
- Сигнал использует только завершённые бары.
- Вход — **open следующего M5-бара**, без лимитов.
- Фиксированный стоп; без трейла и тейка в первом тесте, чтобы не смешивать идею с оптимизацией выхода.
- Стоп на гэпе — по худшему из уровня и open; внутри бара — по уровню.
- Основной расчёт при 3.6 б.п. на круг; стресс при 5.6.
- Заранее фиксированные правила пропусков данных; не отбрасывать событие из-за того, что после входа возник неудобный гэп или плохой бар.
- Сначала считать все сигналы без конкуренции за общий счёт, затем экономику портфеля.
- Для трёх новых идей — одна семья сравнений; если вместе с отдельным fade-тестом ниже, семья из четырёх.

Для первых двух задал бы первичную экономическую планку: **средний gross-результат после стопов не меньше 8 б.п.** Это не прогноз, а требование к запасу:

- net при базовых расходах: около 4.4 б.п.;
- net при стрессе: около 2.4 б.п.;
- при стопе 40 б.п. — приблизительно +0.11R и +0.06R соответственно, без поправки на изменение фактического R от slippage.

Небольшой плюс вроде 1–3 б.п. до расходов — сразу отказ, а не повод оптимизировать тейк.

## 3.2. Стратегия №1: возврат утреннего движения после прихода основной ликвидности

### Механизм

**Предполагаю:** часть движения 07:00–09:50 создаётся менее глубокой ликвидностью и локальным дисбалансом заявок. В 10:00 появляется более широкая встречная ликвидность, и некоторые утренние сдвиги частично возвращаются.

Это не ставка на разворот любого гэпа. Проверяется **движение внутри утренней сессии**, которое основная сессия не подтверждает первым баром.

### Точные правила

Тикеры — все 25, будни, только даты с реально доступной утренней сессией.

1. Утренняя доходность:
   `m = Close(09:45) / Open(07:00) − 1`.
   Здесь Close(09:45) известен в 09:50.
2. Требовать `|m| ≥ 60 б.п.`
3. Первый основной бар 10:00–10:05 должен иметь направление, противоположное m:
   `sign(Close(10:00) − Open(10:00)) = −sign(m)`.
4. В 10:05 войти против m по open следующего бара.
5. Стоп — **40 б.п. от фактического входа**.
6. Выход — в 11:05 по open, если стоп не сработал.
7. Одна сделка на тикер в день. Тейка и трейла нет.

Три потенциально свободных параметра: 60 б.п., 40 б.п., 60 минут удержания. В первом прогоне все фиксированы; сетку не запускать.

**Пример.** От 07:00 цена выросла со 100 до 100.80. Бар 10:00: O=100.80/H=100.85/L=100.60/C=100.70. Вход SHORT на open 10:05; утренний рост является условием, а не доходностью, которую приписывают сделке.

### Масштаб

- **Предполагаю:** потенциальный возврат на таком событии — десятки б.п., ориентир 20–60 б.п., а не 1–3.
- Это амплитуда возможного движения, **не ожидаемая средняя прибыль**.
- Отношение такого движения к базовым расходам: примерно 5.6–16.7.
- При условной частоте 2–6% доступных утренних тикер-дней может получиться порядка **200–600 сделок** на объединённой истории. Частота не измерена.
- Если событий <200, достаточной статистики по принятому здесь протоколу не будет.

### Дешёвая проверка на pandas

Собрать одну строку на тикер-день:

- m;
- знак первого основного бара;
- open 10:05;
- gross-результат до 11:05 со стопом;
- результат без стопа как диагностику;
- MFE/MAE;
- baseline/stress net.

Отдельно показать, сколько движения произошло **до** 10:05: это движение стратегии не принадлежит.

**Бросить**, если при достаточной выборке:

- средний gross после стопов <8 б.п.;
- стресс-net≤0;
- дополнительные 15 тикеров дают неположительный baseline-net;
- результат полностью исчезает без одного тикера или одного временного блока.

### Чем отличается от отвергнутого

От утреннего gap-continuation:

- не используется гэп от вечернего close;
- не покупается подтверждение в 07:00;
- торгуется обратное движение после структурной смены ликвидности в 10:00.

От or-fade:

- нет OR-границы, пробоя и возврата внутрь неё;
- якорь — результат всей утренней сессии и смена торгового режима.

### Главный риск самообмана

Принять новую информацию, накопившуюся утром, за временное ценовое давление. Тогда основная сессия продолжит движение после короткого первого отката.

Другие риски:

- выбирать удачный утренний якорь после расчёта;
- включить аукцион 06:55 в «торгуемое утро»;
- считать отсутствовавшую до 2025-01-27 сессию нулевой доходностью;
- отбрасывать новостные дни по их последующему движению.

### Проверка без чистого временного holdout

Замороженные правила на всех 25 тикерах; основной перенос — на дополнительные 15. Отчёт по фиксированным временным блокам, ресемплирование неделями со всеми тикерами вместе, обязательный стресс расходов.

Это историческая проверка переносимости, не независимое подтверждение. Если прошла — только затем фиксировать будущий paper-период без изменения правил.

## 3.3. Стратегия №2: сворачивание накопленного внутридневного движения перед концом основной сессии

### Механизм

**Предполагаю:** после значительного одностороннего дня часть внутридневных участников уменьшает позиции перед завершением основной сессии. Когда прежний поток перестаёт поддерживать цену, закрытие накопленных позиций создаёт движение против дневного направления.

На Мосбирже нет основания считать, что все обязаны закрыться в 18:30: вечерняя сессия и возможность переноса этому противоречат. Поэтому именно **привязка эффекта ко времени** должна быть проверена, а не постулирована.

### Точные правила

Все 25 тикеров, будни.

1. В 17:30 вычислить:
   - `d = Close(17:25) / Open(10:00) − 1`;
   - `r30 = Close(17:25) / Close(16:55) − 1`.
2. Требовать `|d| ≥ 100 б.п.`
3. Требовать `d × r30 < 0`: последние 30 минут уже направлены против основного движения дня.
4. На open 17:30 войти против d.
5. Стоп — **40 б.п.**
6. Выход — open 18:30.
7. Одна сделка на тикер в день; без TP и трейла.

Не больше четырёх параметров: дневной порог, окно подтверждения, стоп, длительность удержания. Окончание в 18:30 фиксируется как десятиминутный запас до текущего EOD бота; не подбирается по PnL.

### Масштаб

- **Предполагаю:** на выбранных сильных днях рабочая амплитуда возврата может составлять 20–60 б.п.
- Требование к средней реализованной gross-прибыли — те же 8 б.п., а не сама эта амплитуда.
- При условной частоте сигнала 5–12% тикер-дней порядок выборки — **600–1600 сделок** по 25 бумагам.
- Это прогноз количества из предполагаемой частоты, не результат подсчёта.

### Дешёвая проверка

На каждый день посчитать d, r30 и результат 17:30→18:30 со стопом.

Затем выполнить два **заранее заданных диагностических** расчёта с тем же смыслом сигнала в 13:30 и 15:30 и удержанием час. Эти результаты нельзя использовать для выбора нового торгового времени.

Вопрос диагностики: есть ли добавочный эффект конца основной сессии или мы видим обычный откат после большого дневного движения?

**Бросить**, если:

- primary gross<8 б.п. или stress-net≤0;
- на дополнительных 15 нет положительного baseline-net;
- эффект времени не проявляется, а результат не отличается от одинаково построенного обычного внутридневного разворота;
- весь плюс относится к нескольким совместным рыночным дням.

### Отличие от отвергнутых идей

- Не догоняющая бумага после одного рыночного M5-импульса.
- Не кросс-секционный остаток за 15 минут.
- Не continuation после объёма.
- Сигнал основан на **накопленном движении основной сессии**, смене его направления и конкретном окне закрытия экспозиции.

Это различие не гарантирует успеха. Если временная привязка ничего не добавляет, гипотеза о сворачивании позиций не получает поддержки.

### Главный риск самообмана

Постфактум выбрать час, в который развороты сильнее, а затем придумать объяснение про принудительное закрытие.

Также нельзя:

- использовать полный дневной диапазон или дневной close при сигнале 17:30;
- исключать дни с вечерними новостями, узнав о них по последующей цене;
- трактовать коррелированные сигналы десяти бумаг как десять независимых подтверждений.

### Проверка без временного holdout

Те же фиксированные блоки и дополнительные 15 тикеров; семейная поправка вместе с остальными новыми идеями. Недельный bootstrap должен сохранять все сигналы общего рыночного дня вместе.

Не разрешать замену 17:30 на 15:30 по результатам диагностики: это уже новая попытка.

---

## 3.4. Стратегия №3: календарный спрос перед месячной оценкой портфелей

**Это самая слабая из трёх идей по доступной статистике. Я включаю её как дешёвую проверку отдельного механизма, а не как вероятного следующего чемпиона.**

### Механизм

**Предполагаю:** календарные пополнения, ребалансировки и привязка оценки портфелей к концу месяца могут создавать направленный спрос в конце основной сессии, не связанный с последним M5-пробоем.

Систематический положительный знак такого потока на Мосбирже из ваших данных не следует. Его и нужно проверить. Объяснять положительный результат «фондами» без дополнительных наблюдений нельзя.

### Точные правила

1. День события — **последний понедельник–пятница календарного месяца**.
   Он вычисляется календарно, а не выбирается как последний день, оказавшийся в CSV.
2. Если в этот день нет торгов, событие пропускается; на предыдущий доступный день не переносится.
3. На open 17:30 купить равными номинальными долями доступные тикеры заранее фиксированного списка из 25.
4. Стоп каждой позиции — **40 б.п.**
5. Выход — open 18:30.
6. Нет price/volume-фильтра, тейка и трейла.

Никаких подбираемых параметров в первом тесте. Направление long фиксируется заранее; отрицательный результат не превращается автоматически в short-стратегию.

Для проверки сигнала сначала рассчитывается корзина. Исполнимый вариант с ограничением общего счёта оценивается отдельно, без выбора выигравших тикеров.

### Масштаб

- **Предполагаю:** если поток существует, проверяемый средний эффект должен иметь порядок хотя бы 8–12 б.п. gross за час, иначе экономического запаса мало.
- Это требование к гипотезе, не прогноз обнаруженного эффекта.
- Верхняя арифметическая граница raw-наблюдений — около **630 тикер-сделок**: 27 завершённых месяцев ×10 бумаг ядра плюс 24×15 дополнительных, до пропусков.
- Но независимых календарных событий всего около **27 дат**.

**Следовательно, требуемой статистики для уверенного подтверждения здесь не будет**, даже если raw-сделок больше 200. Пятнадцать других бумаг тех же месячных дат не создают пятнадцать независимых календарных экспериментов.

### Дешёвая проверка

Для каждой даты:

- equal-weight gross и net корзины;
- результат на тех же днях недели за одну, две и три недели до события;
- вклад отдельных месяцев;
- baseline/stress.

Главная единица анализа — **дата корзины**, не отдельная акция.

**Бросить**, если:

- net неположителен;
- месячные даты не лучше заранее определённых контрольных дат;
- положительный результат исчезает без одного-двух месяцев.

Даже хороший результат не достаточен для включения в Go на этой истории: он даст основание искать более длинную историю либо иной независимый материал.

### Отличие от отвергнутого

Нет сигнала по импульсу, пробою, относительному отставанию или утреннему гэпу. Проверяется заранее известный календарный поток.

### Главный риск самообмана

- Выбрать после просмотра данных конец месяца, квартала, пятницу или другой календарный день.
- Выдать сотни коррелированных акций за большую выборку.
- Определить «последний торговый день» по будущему наличию баров.
- Выбрать только месяцы с ожидаемым положительным потоком.

### Честная проверка без holdout

Только замороженный тест с явным признанием малой календарной выборки и включением в общую поправку за новые идеи. Историческая cross-validation не создаст недостающие независимые месяцы.

## 3.5. Отдельно: как проверять «фейд пробоя», если идея появилась после просмотра результатов

**Главное: нельзя сделать этот исторический тест независимым одним лишь документом, написанным перед следующим запуском.** Идея уже выбрана по данным. Предрегистрация теперь ограничит дальнейшую подгонку, но не отменит первоначальный отбор.

Я бы сделал следующее.

### 1. Зафиксировал одну конкретную версию

Например:

- будни, все 25 тикеров;
- диапазон 10:00–10:30 по полностью завершённым шести барам;
- с 10:30 до 12:00 — первый close выше верхней или ниже нижней границы;
- **сразу против пробоя** на open следующего бара;
- стоп 40 б.п.;
- выход через 30 минут по open;
- без TP и трейла;
- максимум одно событие на тикер-день.

Это отличается от текущего or-fade: **не ждать будущего возврата внутрь диапазона**. Иначе тест отвечает уже на другой вопрос — о подтверждённом ложном пробое.

Все числа фиксируются один раз. Не проверять сначала 15 вариантов диапазона и затем регистрировать победителя.

### 2. Не определять «ложный пробой» по будущему пути

В выборку входят **все** qualifying пробои, включая те, после которых цена продолжила движение и выбила контртрендовый стоп.

Запрещённая разметка: «возьмём пробои, вернувшиеся в диапазон за следующие 20 минут, и продадим на первоначальном пробое». Именно она способна дать красивую, неисполнимую статистику.

### 3. Отделил primary-выход от диагностики

Primary — 30 минут со стопом 40 б.п.

Доходности через 5, 15 и 60 минут можно показать как форму реакции, но нельзя выбрать лучший горизонт после просмотра и объявить его результатом первичного теста.

### 4. Проверил именно реализуемый разворот после следующего open

Отрицательный результат long-пробоя не означает равный положительный результат short-фейда:

- обе стороны платят издержки;
- стопы и время выхода меняют распределение;
- часть наблюдавшегося разворота могла произойти между сигнальным close и доступным входом.

Нужно считать новую сделку, а не менять знак старого PnL.

### 5. Заранее определил отказ

- <200 сделок — недостаточно данных по принятому протоколу.
- Gross после стопов <8 б.п. — экономически слабый кандидат.
- Stress-net≤0 — отказ.
- Дополнительные 15 дают baseline-net≤0 при достаточной выборке — отказ от универсального механизма.
- Плюс держится на одном тикере или блоке — не принимать.
- Не проходит поправку в семье новых гипотез — не считать подтверждённым.

### 6. Честно назвал статус результата

Даже если всё прошло:

> «Замороженная контртрендовая гипотеза устойчива на повторно используемой истории и переносится на другие бумаги».

Не:

> «Получено независимое доказательство преимущества».

Для последнего нужны новые наблюдения, которых не было при формировании идеи. Пока их нет, разумный следующий шаг — фиксированный paper-протокол, а не ещё один поиск порогов на старых CSV.

---

## Что проверил бы первым

**Возврат утреннего движения после открытия основной сессии.**

Причины:

1. Есть конкретная внешняя граница механизма — 10:00, а не найденная по PnL длина окна.
2. Идея не повторяет проверенное продолжение утреннего гэпа.
3. Вход рыночный, сигнал полностью известен к следующему open.
4. Проверяется движение масштаба десятков б.п., способное пережить расходы.
5. Реализация проверки короткая: одна строка на тикер-день, один час удержания, один фиксированный стоп.
6. Отрицательный результат легко интерпретировать и трудно «спасти» незаметной перенастройкой.

**Но первым техническим действием перед оценкой старого портфеля я бы исправил классификацию `EntryAtBarClose` и посчитал число затронутых ORC-сделок. При +0.032R это может изменить всю исходную оценку ещё до исследования новых идей.**
