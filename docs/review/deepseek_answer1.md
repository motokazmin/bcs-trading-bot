Ниже — только то, что подтверждается кодом в приложенном бандле. Гипотезы, которые не удалось заякорить цитатой, вынесены отдельно.

## Находка 1. Live проверяет тейк по close бара фила, backtest — нет

**Утверждение.** На баре лимитного фила live после `SameBarExitAfterFill` дополнительно гоняет `checkSLTP` по текущей цене (= close бара), а `checkSLTP` проверяет и тейк. Backtest после `SameBarExitAfterFill` ничего больше не делает. Спецификация п.7 («В баре фила проверяется только стоп») соблюдается в backtest и нарушена в live.

**Код.**

`internal/strategy/selfmanaged/selfmanaged.go:311–326`
```go
if reason := position.SameBarExitAfterFill(pos, candle); reason != "" {
    exitPx := position.ExitFillPrice(pos, reason, candle.Close)
    ...
    s.closePosition(ctx, sctx, exitPx, reason)
    return
}
if last := s.currentLastPrice(); last > 0 {
    s.checkSLTP(ctx, sctx, last)
}
```

`internal/backtest/portfolio.go:297–303`
```go
if reason := position.SameBarExitAfterFill(st.position, candle); reason != "" {
    exitPx := position.ExitFillPrice(st.position, reason, candle.Close)
    ...
    p.closePosition(ctx, executor, st, exitPx, reason, candle.Timestamp)
}
```
Аналогично `internal/backtest/runner.go:228–234`.

`checkSLTP` вызывает `position.CheckExit(pos, price)`, который для BUY возвращает `CloseReasonTakeProfit` при `price >= pos.TakeProfit` (`position.go:148–150`). То есть при `candle.Close >= TP` на баре фила live закрывается по TP.

**Сценарий.** ORC BUY, `limit = 100`, `dist = 0.8`, `reward_ratio = 1.5` → `TP = 101.2`, `SL = 99.2`. Бар фила: `O=100.5, H=102.0, L=99.8, C=101.5`. Fill = 100 (`min(O, limit)`). Live: `SameBarExitAfterFill` → Low=99.8 > SL=99.2, нет. `checkSLTP(101.5)` → 101.5 ≥ TP=101.2, выход по TP на баре фила. Backtest: `SameBarExitAfterFill` → нет выхода, позиция держится дальше. Следующий бар `O=100.8, H=101.0, L=99.0, C=99.5` — путь `O→L→H→C`, на `L=99.0` срабатывает SL=99.2, выход по SL. Итог: live **+~1.5R**, backtest **−1R** на одной и той же сделке.

**Как проверить тестом.** Юнит в `internal/backtest/intrabar_test.go` и зеркальный в `selfmanaged`: бары ровно как выше, проверять `CloseReason` и `ExitPrice`. Сейчас теста на «same-bar TP после лимитного фила» нет ни в одном пакете.

**Оценка влияния на exp_R.** Событие редкое (нужно `close ≥ fill + dist·RR` на баре фила, то есть бар должен закрыться почти на максимуме выше TP), но каждое такое событие — разница ~2.5R. При 1500 сделках в портфеле даже 5–10 эпизодов дают смещение **≈ +0.01…+0.03R в пользу live** (live систематически переоценивает себя относительно backtest). **Уверен** в факте расхождения; в цифре — **предполагаю**.

## Находка 2. Live проверяет новый стоп по close бара трейла, backtest — только со следующего бара

**Утверждение.** После пересчёта трейла на закрытом баре live сразу сверяет новую SL с текущей ценой (= close того же бара). Backtest применяет трейл в конце `processIntrabar` и проверяет новый SL только по пути следующего бара (`i=0` — open). Спецификация п.4 («новый стоп действует со следующего бара») в live нарушена.

**Код.**

`internal/strategy/selfmanaged/selfmanaged.go:401–411`
```go
trailing.Apply(s.pos, position.TrailPrice(candle, s.pos.Direction), s.cfg.TrailCfg)
...
// Новый стоп мог оказаться за текущей ценой — выход по рынку, как open следующего бара в backtest.
if last := s.currentLastPrice(); last > 0 {
    s.checkSLTP(ctx, sctx, last)
}
```

`internal/backtest/portfolio.go:320–321`
```go
// Трейл — по закрытому бару, как в live (selfmanaged.trailOnBar).
trailing.Apply(pos, position.TrailPrice(candle, pos.Direction), st.cfg.TrailCfg)
```
Никакого `CheckExit` с `candle.Close` после `Apply` в backtest нет.

**Сценарий.** BUY вход 100, R=1, breakeven 100.05. Бар: `O=100.0, H=101.5, L=99.5, C=99.8`. MFE=101.5 ≥ 101 → трейл активируется, SL переезжает в 100.05. Live: `checkSLTP(99.8)` → SL сработал, выход по 99.8. Backtest: новый SL не сверяется с close; следующий бар `O=100.3 > 100.05` (гэп вверх через ночь или дыра в данных) — позиция остаётся открытой. Расхождение только на разрыве между барами; на непрерывных M5 обычно совпадёт (next open ≈ close), но на первых барах утра/вечера и на дырах — нет.

**Как проверить.** Юнит: серия из двух баров с зазором между close первого и open второго, `trailActivationR` подобран так, чтобы новый SL оказался выше close первого и ниже open второго. Сейчас `intrabar_test.go:62–97` проверяет ровно обратный случай (open **ниже** нового стопа) и потому расхождение не видит.

**Оценка.** Затрагивает единичные сделки на гэпах; **уверен**, что расхождение есть, но **предполагаю** вклад ≤ 0.005R на портфельный exp_R.

## Находка 3. Проскальзывание накладывается на цену лимитного фила

**Утверждение.** Для ORC фил считается в `orcPendingLimit.fillPrice` как `min(O, limit)` / `max(O, limit)`, а затем в общем `processCandle` к нему применяется `costs.FillPrice`, то есть фил уезжает **за** лимит. Реальный лимит так исполниться не может: он либо исполняется по уровню/лучше, либо не исполняется.

**Код.**

`internal/strategy/opening_range_continuation.go:95–109`
```go
case "BUY":
    if candle.Low > p.limitPrice {
        return 0, false
    }
    return math.Min(candle.Open, p.limitPrice), true
```

`internal/backtest/portfolio.go:254` (и `runner.go:195`, `selfmanaged.go:247`)
```go
fillPrice := costs.FillPrice(st.cfg.CostsCfg, signal.Direction, signal.Price)
```

Комментарий в `configs/runs/portfolio-paper.yaml:37–40` утверждает, что для ORC «вход так оценивается с запасом», но это верно лишь для выхода; цена **входа** смещается против лимита.

**Сценарий.** BUY-лимит на 100, `slippage_bps=1`. Заявка исполнилась по `min(O,100)=100`. После `FillPrice` цена входа = `100·(1+1e-4)=100.01` — выше лимита. R становится `100.01 − SL` вместо `100 − SL`, TP в R-единицах сжимается.

**Как проверить.** Юнит в `internal/strategy/opening_range_continuation_test.go` и в `internal/backtest/intrabar_test.go`: задать `SlippageBps=1`, лимит на 100, бар с `Low=99.5, Open=100.5` — проверить, что `EntryPrice <= 100`. Сейчас такого теста нет.

**Оценка.** Систематическое сжатие выигрышей в R примерно на `slip/stop_frac ≈ 1bp / 100bp = 1%` (для стопов в 1%) и нейтрально для проигрышей в R (при `EntryPrice` и `SL`, заданных стратегией, `−1R` остаётся `−1R`). На ORC с exp_R ≈ −0.024…+0.1 эффект **≈ +0.001…+0.005R** в пользу стратегии, если считать правильно. **Уверен** в факте, **предполагаю** в оценке.

## Находка 5. Live-`checkEOD` не имеет проверки «новый день», которую имеет backtest-`closeMissedEOD`

**Утверждение.** Backtest закрывает позицию, пережившую EOD из-за дыры в данных, по close предыдущего бара через `closeMissedEOD` (условие `newDay || ShouldForceClose`). Live-`checkEOD` проверяет только `ShouldForceClose(now)`. Если дыра в данных перешагнула полночь (вечерняя сессия `19:05–23:50`, следующий бар — `07:00`), `ShouldForceClose(07:00)` = false, и live **не закроет** позицию. В реальном live её закроет `eodTicker` через 30 с после 23:50, но в реплей-тесте `eodTicker` не эмулируется.

`internal/backtest/portfolio.go:220–228`
```go

if newDay || st.session.ShouldForceClose(candle.Timestamp) {
    p.closePosition(ctx, executor, st, st.lastClose, models.CloseReasonEOD, st.lastBarEnd)

```

`internal/strategy/selfmanaged/selfmanaged.go:414–429`
```go
func (s *SelfManagedStrategy) checkEOD(ctx context.Context, sctx contract.StrategyContext, price float64, now time.Time) {
    if !s.cfg.Session.ShouldForceClose(now) {
        if s.cfg.Session.EntriesAllowed(now) {
            s.eodCloseDate = ""
        }
        return
    }
    ...
}
```
Проверки «новый день» нет.

**Как проверить.** Расширить `session_time_test.go:98–113` (`TestMissedEODClosesAtLastClose`) аналогом для live-методов: прогнать бары `23:20`, `23:25`, `07:00` через `SelfManagedStrategy.checkEOD/trailOnBar/processCandle` с фейковым `SessionClock`, где `IsSessionOpen(07:00)` true для morning-слота. Сейчас `replay_history_test.go` вызывает live-методы, но без `eodTicker` и без данных с ночным разрывом в EOD-окне, поэтому расхождение не ловится.

**Оценка.** Только в редком сценарии с дырой в данных на границе EOD. **Уверен** в факте расхождения между backtest и эмуляцией live; **предполагаю**, что на портфельный exp_R влияет слабо.

**Оценка.** Влияние на exp_R небольшое (CB срабатывает редко), **≈ 0.001–0.005R**. **Уверен** в факте.

## Гипотезы, не подтверждённые цитатой

1. **`min_stop_bps`-инвариант в YAML неточен.** В `configs/runs/portfolio-paper.yaml:46–52` утверждается, что кап по кэшу не срабатывает при `risk_per_trade_percent ≤ min_stop_bps/100`, но `CapQuantityByCash` применяется к `balance × 0.95`, а не к полному депозиту (`selfmanaged.go:258`, `risk/manager.go:64–80`). Похоже, при стопе ровно 20 б.п. и риске 0.2% cap всё же сработает. Проверить не могу без развёртки по данным.

2. **Приоритет слотов на одном тикере.** В backtest `byTicker[ticker]` упорядочен по `slotKey` (`portfolio.go:64–72`), в live — по мере итерации `map` при подписке. Если два слота хотят войти в один тикер в один бар, в разных путях побеждает разный слот. Влияние не оцениваю без логов `TickerBusySkips` по слотам.

3. **Tick vs бар в live-`checkEOD`.** Используется `time.Now()`, а не время тика; при задержке фида EOD может сработать по wall-clock раньше, чем «по расписанию». Не подтверждается без кода `sctx.Ticks()`.

### `intrabar_test.go`

Покрывает: переезд трейла на закрытии бара, гэп-исполнение стопа по `open` следующего бара, оба пути (`runner` и `portfolio`).

Покрывает: совпадение live и backtest поштучно на истории для боевого конфига.

Не покрывает и может остаться зелёным при поломке:
- Находку 1. Тест сверяет `CloseReason` и `ExitPrice`, но не `ClosedAt`. Если live закрывается по TP на баре фила, а backtest — по TP на следующем баре по той же цене, тест считает их совпавшими. Если же backtest закрывается по SL, тест поймает расхождение — но только если такой бар попадёт в `data/history`. Утверждать, что он там есть, не могу.
- Находку 2. Тест интерполирует тики так, что последняя точка пути — `c.Close`. Значит, `checkSLTP` по close эквивалентен проверке последнего тика; trail-on-bar применяется **до** `processCandle`, но сверка новых стопов с close всё равно играет роль только на разрыве между барами, а в синтетике разрывов нет.
- Находку 5. `eodTicker` не эмулируется, ночные дыры в EOD-окне — тоже.
- Приоритет слотов на тикере тест **фиксирует по алфавиту** (`replay_history_test.go:98`), то есть маскирует расхождение с live, где порядок случаен.

**Мутационная проверка, которую стоит добавить:** явный тест «live-`processCandle` без `checkSLTP` после открытия позиции» должен ломать именно сравнение live↔backtest на сценарии находки 1. Сейчас такого теста нет.

## Ответы на вопросы раздела 8

### 1. Есть ли ещё места, где решение внутри бара зависит от его исхода?

Есть два, оба — в live, оба связаны с использованием `currentLastPrice()` = close бара как «цены сразу после бара»:

- Находка 1: `checkSLTP(last)` после открытия лимитной позиции (`selfmanaged.go:324–326`). Решение о выходе по TP принимается по `candle.Close`, то есть по исходу бара.
- Находка 2: `checkSLTP(last)` после `trailing.Apply` (`selfmanaged.go:409–411`). Новый стоп сверяется с close бара, на котором он взведён, хотя спецификация п.4 говорит «со следующего бара».

Оба случая формально «решения на закрытии бара», но нарушают правило тем, что в backtest то же решение отложено. Кроме этих двух — не нашёл.

### 2. Корректна ли схема «стоп/тейк фиксированы внутри бара, трейл — по закрытому бару»?

Как модель — да, она симметрична и не даёт матожидания до издержек на мартингале (это подтверждает п.4.1 брифа). Но она **не совпадает** с живым брокером, где трейл переставляется по тикам и любой тик между двумя барами может выбить по новому стопу. Раз вы сознательно привели live к модели, а не наоборот — это чистое решение, но оно систематически **оптимистично** для трейла: живая торговля будет выбивать чаще на «шумных» тиках внутри бара, которых модель не видит. Формально: на мартингале такое искажение компенсируется симметрией O→L→H→C и O→H→L→C на серии, но на реальных данных с кластеризацией волатильности и автокорреляцией симметрии нет. Заменять не предлагаю, но **живой результат по слотам с `trail_stage_max ≥ 2` стоит ожидать хуже baseline**.

### 3. Как честно моделировать исполнение лимита при касании без тиков?

Из трёх вариантов (N тиков, вероятностная модель по объёму, «касание = фил») наиболее защитимый — **вероятностная модель, зависящая от того, как глубоко бар прошёл уровень и с каким объёмом**:

- Если `Low` бара строго ниже лимита на ширину, соизмеримую с ATR M5 (например, ≥ 0.2 ATR), заявка исполнена.
- Если `Low` ровно касается лимита — вероятность исполнения ~0.5, зависящая от отношения объёма бара к среднему за N.
- Если бар открылся уже за уровнем (`Open < limit` для BUY) — исполнение по `Open` детерминировано (это уже реализовано в `fillPrice`).

Конкретно для ORC это важно, потому что ретест-лимит систематически получает **худшие** сделки: когда рынок возвращается к границе диапазона, это часто уже не продолжение, а разворот. Если часть этих филов «не случается» в реальности (нет очереди, нет объёма), ORC в бэктесте переоценён. Проверяемая гипотеза: при «касание = 50% фила» exp_R `orc-complement` падает. Прогнать с `limitFillProbability=0.5` в симуляторе и сравнить.

### 4. Стоит ли кормить стратегию всеми барами?

Да, стоит — и это дёшево. Сейчас `processCandle` вызывается только когда `st.position == nil` (`portfolio.go:213–214`, `selfmanaged.go:204`). Это значит, что `candleBuffer` стратегии заполняется с дырами ровно там, где сама стратегия была в позиции. ATR, `rangeLevels`, `calcSMA` на дырявой истории дают другой результат, чем на полной, и этот сдвиг **зависит от её же сделок** — то есть в исследовании это эндогенная ошибка. Чинить по образцу `trailOnBar`: кормить `OnCandle` на каждом баре, но с гейтом на возврат ордера — «если есть позиция, игнорировать сигнал». Это не меняет сегодняшний сигнал на входе (в момент входа позиции нет), но выравнивает индикаторы. Риск: сломается логика `isDuplicateUpdate` — она завязана на `lastSignalTime`, который сейчас ставится только на бары сигналов. Нужно аккуратно разнести «проглотить бар» и «не выдавать сигнал». Проверить тестом: прогнать нулевую модель с случайным входом на полной истории и с текущим «голодным» режимом — exp_R до издержек должен совпасть с точностью до шума.

### 5. Влияет ли приоритет слотов?

Влияет на **конкретные сделки** — те, где два слота хотят зайти в один тикер на одном баре. Backtest берёт алфавитный порядок (`portfolio.go:64–72`, `portfolio.go:212`), live — порядок итерации map, то есть недетерминирован. Если это событие редкое, exp_R портфеля стабилен, но сравнение live↔backtest поштучно может расходиться. Нужен явный приоритет: например, по убыванию «ожидаемой ценности слота» (исторический exp_R × число сделок) с тай-брейком по алфавиту. Это детерминирует обе стороны. Без изменения кода проверить нечем; с изменением — прогнать реплей и убедиться, что `TickerBusySkips` приписан разумным слотам.

### 6. Бумага vs биржа для ORC

Вижу три расхождения сверх уже перечисленных в брифе:

- **Нет отмены заявки по времени суток** в реальной биржевой логике, кроме `hourEnd` (`opening_range_continuation.go:281–284`). Сейчас заявка живёт до конца часа; если пробой был в 14:55, заявка умрёт в 15:00 — с одной стороны ок, с другой, тест показывает, что закрытие сессии может быть раньше. Явного гейта «не ставить заявку, если до EOD меньше N минут» нет, полагается на `EntriesAllowed` для момента постановки; но отмену висящей заявки при наступлении EOD никто не делает — она проживёт до `hourEnd`, что может быть после EOD.
- **Учёт очереди.** Лимит на самом уровне в реальной книге не исполнится, если на уровне уже стоит очередь покупателей; бэктест считает, что исполнится. Для ORC это критично (см. п.3).
- **Заявка выставляется по close бара пробоя, а не по тику.** В бэктесте уровень фиксирован на `orbHigh`/`orbLow` предыдущего бара. В live между «решением» (close бара) и «постановкой заявки» проходит задержка, за которую диапазон мог сместиться, а заявка выставится по старому уровню. Явного гейта «если рынок ушёл от уровня на > X ATR, не ставить» нет.
