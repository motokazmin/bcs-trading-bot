# 0024 — Выход по стопу: live против уровня (наблюдение к paper-m15)

Дата: 2026-10-08. Выборка: paper-m15, сделки 2026-10-05 → 10-08 (7 шт.), снимок боевой БД,
сырой WS-поток `data/ws-raw/2026-10-05.jsonl.gz` с сервера.

**Регистрацию [0019](0019-paper-m15-registration.md) не меняет.** Это дополнительная метрика, а не
критерий. Решение по этапу 1 принимается только по пунктам 0019.

## Контекст

При поштучной сверке с `portfolio-backtest` выходы по стопу разошлись в обе стороны:

- **#108 TATN, BUY:** стоп после трейла 641.19, live вышел по 640.74 (−0.09R). Backtest вышел по уровню
  минус проскальзывание, 641.13 (+0.06R). По WS: котировки приходят раз в секунду, и за одну секунду
  `last` упал с 641.5 до 640.8. Bid в эту секунду был 640.9–641.0, так что реальная рыночная продажа
  была бы между результатами live и backtest.
- **#107 AFKS, SELL:** стоп шорта 7.076, high бара 11:00 — 7.077. Максимум `last` и ask за бар в
  потоке котировок — 7.075 (655 котировок): сделку по 7.077 бот не увидел. Backtest закрылся по стопу
  (−1.12R), live пережил бар, и его позже закрыл трейл (−0.10R).

Это не баг симуляции. Live отражает, как устроен бот: стоп ведёт сам бот по снимку котировки раз в
секунду и закрывается рыночной заявкой. Backtest моделирует стоп-заявку, стоящую на бирже. На быстром
движении бот выходит хуже уровня, короткий выброс между снимками пропускает. Знак суммарного
эффекта по двум случаям неизвестен.

## Решение

В `make analyze` добавлен раздел «Выход по стопу: live против уровня» (`scripts/analyze-trades.py`):

| Метрика | Как считается |
|---|---|
| хуже уровня, внутри бара | б.п. между `final_stop_loss` и ценой выхода по стопу, когда бар выхода открылся до стопа; в backtest это ровно `slippage_bps` |
| бар выхода открылся за стопом | гэп или трейл, поставленный за ценой (#107, #113): backtest берёт ту же худшую цену, сравнивать не с чем |
| стоп пропущен | бар между входом и выходом прошёл **исходный** стоп, а выхода не было. Трейл стоп только подтягивает, значит, это оценка снизу |

Код торговли не менялся.

На 7 сделках: внутри бара 2 выхода, хуже уровня в среднем на +4.2 б.п. против 1.0 в backtest. Бар выхода
открылся за стопом у 2 выходов. Стоп пропущен у 1 сделки из 7 (#107). На такой выборке выводов нет.

## Последствия

- **На этапе 1 (≥ 50 сделок) смотреть, насколько «внутри бара» хуже `slippage_bps`.** Чувствительность
  ≈ −0.10R на каждый б.п. Если live стабильно на 1–2 б.п. хуже уровня, backtest и `docs/baseline.md`
  завышают результат на ~0.1–0.2R на сделку. Проверять перед тем, как ссылаться на baseline.
- **До реальных денег решить, где живут стопы:** у бота (как сейчас) или биржевыми заявками.
  Если на бирже — правильная модель у backtest, а `virtual` надо подтянуть к ней. Если у бота — backtest
  должен моделировать выход по снимку котировки, а не по касанию high/low. Механика держится в трёх
  местах синхронно (CLAUDE.md), правка одного из них — только вместе с остальными.
- Котировки с bid/ask пишутся на сервере (`data/ws-raw`), каждый спорный выход можно разобрать по ним.
